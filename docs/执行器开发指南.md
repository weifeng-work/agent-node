# 执行器开发指南

> 本文面向想为 agent-node 开发执行器插件（Executor Plugin）的开发者。
> 执行器 = 一个可被节点调用、能「执行一次 AI 任务并产出结果文件」的后端实现。
> 官方适配器（WorkBuddy / CodeBuddy CLI / TUI）均为同一接口编写，可作为最佳范例。

配套阅读：[executors/base.py](../executors/base.py)（接口真身）、[executors/registry.py](../executors/registry.py)（加载与状态机）。

## 一、执行器是什么

在一个 agent-node 节点里，执行器（executor）是「**真正跑 AI 任务的工人**」：
外部智能体（经 MCP / CLI / 面板）把任务提交给节点，节点把任务转交某个执行器，
执行器负责干活（如调用某 AI 客户端、跑某个命令行），并把最终结论写入**结果文件**。

同一节点可挂多个执行器（如同时有 WorkBuddy 和 CodeBuddy）。每个执行器有一个
**agent_id**（插件标识），节点据此路由任务、隔离工作目录、广播能力。

## 二、接口总览（设计 2.2.15，绑定契约）

插件用 **Python 编写**，继承 `executors/base.py` 的 `ExecutorPlugin`。契约分
「绑定（MUST）」与「自由（施工定）」：
- **绑定**：类属性 `plugin_id / display_name / executor_type / concurrency`；
  三个抽象方法签名 `check_capability / submit` 必须与文档一致；结果文件契约语义。
- **自由**：方法内部怎么实现（怎么调 GUI、怎么起子进程、怎么轮询）完全由你定。

### 2.1 类属性

| 属性 | 类型 | 说明 |
|---|---|---|
| `plugin_id` | str（必须） | 插件唯一标识，用作 agent_id，如 `"my-exec"` |
| `display_name` | str | 人类可读名，面板展示用 |
| `executor_type` | str | `interactive_tui` / `non_interactive_cli` / `gui` |
| `concurrency` | int | 并发上限（见第四节） |

### 2.2 生命周期钩子

| 方法 | 时机 |
|---|---|
| `__init__(ctx)` | 注册表实例化时，`ctx` 为 [PluginContext](#31-plugincontext) |
| `on_load()` | 加载成功、能力自检通过后调用一次（可选，默认空） |
| `on_unload()` | 卸载 / 重扫时调用（可选，默认空） |
| `check_capability()` | **必须实现**，启动自检 |
| `submit(task)` | **必须实现**，收到任务即开始运行 |
| `is_done(task_id)` | 默认：结果文件已生成（多数场景无需改）|
| `get_result(task_id)` | 默认：读取结果文件内容 |
| `status()` | 默认报 idle/busy；如需更精细可覆盖 |

### 2.3 数据类（传入 Python 对象，均来自 base.py）

#### 3.1 PluginContext
```python
PluginContext(node_id, agent_id, work_dir, config)
# work_dir: 本插件专属工作目录 Path（结果文件/附件就放这）
# config:   插件配置 dict（含授权对话框匹配等启动参数）
```

#### 3.2 CapabilityResult（check_capability 返回值）
```python
CapabilityResult(available: bool, reason: str | None = None, premises: list[str] | None = None)
# available=False 时节点不广播该能力；reason 记录原因；premises 是前提披露（如"需安装 xx"）
```

#### 3.3 TaskInput（submit 入参）
```python
TaskInput(task_id: str, prompt: str, attachments: list[str],
          result_file: Path, timeout: float)
# prompt:      给 AI 的完整提示词（已含"把最终结论写入结果文件"指令）
# attachments: 附件在本地 work_dir 的路径列表（随任务直传，2.13.1）
# result_file: 结果文件的绝对路径 Path——你必须把结论写入这里
# timeout:     超时（秒）
```

#### 3.4 SubmitResult（submit 返回值）
```python
SubmitResult(ok: bool, error: ErrorCode | None = None, detail: str | None = None)
# ok=True 表示"任务已受理/已开始"，不是"已完成"
# error 取 ErrorCode: offline/disabled/not_installed/busy/suspended/timeout/agent_error
```

#### 3.5 ResultPayload / ExecutorStatus
```python
ResultPayload(ok, error, content)      # 结果文件内容读取结果
ExecutorStatus(available, state, inflight, concurrency, current_task, queue_len, until)
# state: 插件只报 idle/busy；suspended 由节点核心叠加
```

## 三、结果文件契约（核心概念，2.2.11）

**一切执行器结果必须经「结果文件」回收**。约定：

1. `submit()` 收到任务后，全力以赴执行 `task.prompt`。
2. 执行完成后，把最终结论写入 `task.result_file`（建议原子写：先写 `.tmp` 再 rename）。
3. 节点判定完成的默认方式：`is_done` → 结果文件存在，且大小连续 2 轮稳定（注册表轮询）。
4. 成功时 `get_result` 读该文件内容返回给调用方。

> 为什么用文件契约而非直接返回：GUI/交互式执行器（如 WorkBuddy）是"注入操作别人的
> 窗口"，无法同步拿返回值——文件是跨进程、跨等待最稳的传递方式。

## 四、三种执行器类型与并发语义

| executor_type | 典型实现 | node 端并发处理 |
|---|---|---|
| `non_interactive_cli` | 非交互命令行（如 codebuddy-cli `-p`） | **并发 N**（=concurrency），满则 busy 拒绝不排队 |
| `interactive_tui` | 常驻交互终端会话（如 codebuddy-tui） | **并发 1**，串行排队（常驻会话复用） |
| `gui` | 桌面 GUI 自动化（如 WorkBuddy UIA） | **并发 1**，串行排队 |

- 非交互 CLI 因每任务独立进程，可并发（默认 3）。
- 交互 TUI / GUI 是"复用一个窗口/会话"，必须串行，节点会帮你排队。

## 五、如何让节点识别你的插件（4 种方式）

1. **内置适配器**：把类放在 `executors/adapters/`，并在 `registry.py` 的 `load_plugins()`
   里 import 后 `_add_plugin(MyPlugin, "<agent_id>", {})`。适合随项目发布的执行器。
2. **外部插件（推荐给用户自定义）**：把 `.py` 文件放进**本机** `data/plugins/`，
   重启节点（或经 `plugin_sync` 分发后重扫）即自动加载。
   外部插件要求：是 `ExecutorPlugin` 的子类、有 `plugin_id`、且模块不属于
   `executors`/`node` 包内部。agent_id 取 `agent_id` 属性值，否则取 `plugin_id`。
3. **配置 CLI 条目**：在插件配置 `cli_executors` 列表加一条 `{agent_id, command}`，
   节点用 `CliExecutorPlugin` 以指定命令运行（适合包装任意命令行）。
4. **mock**：测试桩，`node_config.json` 的 `enable_mock` 默认 true。

> 用户自定义插件零侵入：**不需要改项目源码**，只需把一个 `.py` 丢进
> `%LOCALAPPDATA%\agent-node\data\plugins\` 即可被加载。

## 六、最小插件示例

把下面代码保存为 `data/plugins/hello.py` 并重启节点，即得到一个 `hello` 执行器。

```python
"""示例外部插件：把收到的提示词原样回显到结果文件。"""
from __future__ import annotations
from pathlib import Path
from executors.base import (
    CapabilityResult, ExecutorPlugin, SubmitResult, TaskInput)


class HelloPlugin(ExecutorPlugin):
    plugin_id = "hello"
    display_name = "Hello"
    executor_type = "non_interactive_cli"
    concurrency = 3

    def check_capability(self) -> CapabilityResult:
        # 永远可用；premises 披露给调用方
        return CapabilityResult(True, premises=["无需外部依赖"])

    def submit(self, task: TaskInput) -> SubmitResult:
        # 注意：本示例是同步阻塞；真实实现可起线程/子进程后立即返回
        try:
            # 把结论写入结果文件（建议原子写）
            tmp = task.result_file.with_suffix(".md.tmp")
            tmp.write_text(f"收到任务 {task.task_id}\n\n{task.prompt}",
                           encoding="utf-8")
            tmp.replace(task.result_file)
            return SubmitResult(ok=True)
        except Exception as e:
            return SubmitResult(ok=False, error="agent_error", detail=str(e))
```

> 说明：本示例同步写出结果文件，`is_done` 走默认（文件存在）即可。真实执行器
> （GUI/CLI 注入）通常异步：`submit` 先返回 `ok=True`，后台线程慢慢干活并写文件。

## 七、最佳实践与坑

- **异步优先**：`submit` 里起线程/子进程后尽快返回 `ok=True`，避免阻塞节点事件循环。
- **结果文件原子写**：`.tmp` 写完后 `rename`，防止节点读到半截文件。
- **能力自检要诚实**：`check_capability` 检测「此刻能否干活」（CLI 是否在 PATH、
  GUI 是否在运行），不行就 `available=False` 并给 `reason`，别广播假能力。
- **附件处理**：`task.attachments` 已在你的 `work_dir` 下，直接读即可。
- **GUI 注入（2.2.14）**：涉及授权/登录对话框时，用 `ctx.config` 里的匹配规则自动
  跳过；输出对方登录态时给明确 `auth_required` 指引，别把「登录过期」当任务失败。
- **并发别超**：`non_interactive_cli` 设 `concurrency` 后，注册表用信号量强制，你
  无需自行加锁，但内部别占着不还（保持 submit 快速返回）。
- **错误码语义**：`busy` = 并发满且不排队；`suspended` = 被人类挂起；`timeout` =
  跑超时；`agent_error` = 执行期出错；不要混用，面板/MCP 会按码提示用户。

## 八、调试

- 节点日志（`data/node.log`）会记录插件加载成功/失败、能力自检结果。
- 面板「执行器」视图可看每个执行器的 available / state / concurrency / premises。
- `data/executor_work/<agent_id>/<task_id>/` 是本任务的工作目录，结果文件、附件都在其中。

## 九、外部插件协议（plugin_sync 分发，2.2.10）

插件可在节点间 `plugin_sync` 分发（受 `allow_file` 开关管辖，分发到目标机
`data/plugins/`）。目标节点 `rescan` 时新增纳入；
注意：`interactive_tui` / `gui` 类插件重扫后需重启对应进程才生效。
