# Agent Node 去中心化重构设计

日期：2026-08-19（2026-08-20 修订：落地一致性 / 命名歧义 / 架构可行性评审结论）
定位：把现有中心化（依赖单一 hub）的 agent-node 重构为去中心化的「AI 可控的加强版 LocalSend」。

---

## 一、总纲（工程原则）

- **极简拓扑**：去掉单一 hub，采用最简对等 mesh。通信层用 **TCP 极简实现**（点对点明文），不做每节点 broker。
- **纯明言传输**：明文、显式寻址，不加密、不认证包装。
- **全放开权限**：自用局域网内全放开，不做鉴权限制。
- **所有执行器不用任何隐藏**：CLI、GUI 都可见。

## 第零章、用户故事

从用户视角提炼的需求总结（"在 X 情景下，做 Y 操作，看到 Z 发生"）。技术条目见第二章。

### 部署与启动
- **US-1** 安装节点：用户想在自己电脑上加入协作网络 → 执行一行命令 → 自动下载源码、装依赖、桌面出现快捷方式。
- **US-2** 启动节点：用户双击快捷方式 → 节点后台启动（无黑窗口）、浏览器自动打开面板、面板显示节点在线。
- **US-3** 重复启动：用户忘了节点已在运行又双击 → 不产生第二实例，而是**直接打开面板**（2.11.2）。

### 发现与连接
- **US-4** 自动发现：用户在两台电脑都启动节点 → 各自面板节点列表自动出现对方（无需配置 IP/端口），显示**名称与 node_id**、在线、能力。
- **US-5** 下线检测：某电脑关机 → 其他节点面板其状态从在线变离线（延迟数秒）。
- **US-6** 命名节点：用户想改节点名 → 面板输入并保存 → 其他所有节点自动显示新名称。

### 聊天（类似 LocalSend/微信）
- **US-7** 发文本消息：用户给另一台电脑发消息 → 对方面板出现消息气泡 + 弹系统通知。
- **US-8** 查看聊天记录：用户回看历史对话 → 看到按对方聚合的会话和气泡记录。
- **US-9** 对方离线发消息：用户给离线电脑发消息 → 失败并提示"目标不在线"，记录在案。

### 文件传输
- **US-10** 发文件到收件箱：用户传文件（不指定路径）→ 落到对方 `data/inbox/`。
- **US-11** 发文件到指定目录：用户指定目标路径 → 文件落到指定位置。
- **US-12** 拉取对方任意文件：用户指定对方绝对路径拉取 → 文件（文件夹整树复制、不经打包）落到本机。
- **US-13** 远程文件浏览器：用户像资源管理器一样看对方文件系统 → 浏览/下载/上传。

### 同步文件夹（分布式云空间）
- **US-14** 共享防损：用户把文件拖进 `data/sync/` → 自动通知网络内节点 → 其他节点 `data/sync/` 也出现该文件（防损）。
- **US-15** 定期同步：用户用计划任务定时调 `cli.py sync` → 按计划同步最新文件。

### 远程命令与控制
- **US-16** 远程执行命令：用户向对方发命令 → 对方执行并返回输出。
- **US-17** 受控熔断：用户关闭对应开关 → 开关变化并提示"远程将无法执行命令"，远程请求被拒并记录。

### 调用远程 AI 智能体（执行器）
- **US-18** 调用另一台电脑的 AI：本机 AI 发任务给另一台电脑的智能体 → 目标机弹出可见窗口显示对话过程，完成后回传结果。
- **US-19** 看到非交互调用对话：一次性非交互调用也弹窗显示命令/提示词/输出，完成后停留几秒再关。
- **US-20** 查询执行器忙否：用户查询对方执行器状态 → 返回忙碌/空闲/队列长度。
- **US-21** 执行器未装/未运行：调用对方 AI 但对方无对应智能体或未启动 → 收到明确错误"未检测到/请先启动"，面板显示前提条件。
- **US-22** CLI 需要登录：对方 CLI 需登录 → 执行器返回"需要登录"，psmux 窗口置顶 + 系统通知提醒人类查看窗口登录。

### 异步任务
- **US-23** 发异步任务后继续干活：本机 AI 异步发任务 → 不阻塞继续做别的，回执进异步邮箱，面板/系统通知提醒，下次输入时取回执。
- **US-24** 触发型任务：只想要对方 AI 开始执行、不关心结果 → 触发型发送 → 收到"触发成功"确认信号（或失败原因）。

### 团队隔离
- **US-25** 设置团队隔离：用户有两组电脑不想互相干扰 → 给每组设置 team → 只与同 team 互通；其他电脑**经 beacon 仍可见其在网与 team，但无法建立连接/互通**。
- **US-26** 切换团队：把某电脑从 A 切到 B → 自动断开 A、发现 B；原 team 电脑能看到它"已切到 team B"。

### AI 接入
- **US-27** 让 AI 使用节点能力：本机 AI 操作节点 → 通过 MCP 工具（AI 加载 skill 说明书学会怎么用）→ AI 调用并报告结果。
- **US-28** AI 不擅自改节点程序：skill 明确"只能经标准接口操作，不得改源码/打补丁"。
- **US-29** 已连节点离线不消失：用户曾连上的电脑关机 → 面板该节点仍显示为"离线 + 上次在线时间"，不消失；可手动"忘记节点"。
- **US-30** 语义化调用：本机 AI 用**结构化工具**（同一方式）调用任意执行器（本机或远程），无需拼长命令行/裸 JSON 报文。

## 二、确认为需求的功能清单

以下每一条均为对话中你已确认/确定的要求。编号采用**树形三段式**（章.节.条，如 2.3.1），新增需求只在对应小节追加新条，不影响其他小节编号。原子化 Given/When/Then 条目跟随所属小节编号。

### 2.1 去中心化
- **2.1.1** 去中心化重构，去掉单一 hub 单点。
- **2.1.2** 不引托盘菜单（取消托盘，降低维护/测试难度）。
- **2.1.3** **节点改名能力**：本节点显示名**仅由本机**（本机面板/本机 AI）修改并持久化，随 beacon 广播，对端节点自动显示新名称；**远程不可改**。
- **2.1.4** **跨网段不列为需求**：自动发现仅覆盖同网段（UDP beacon 广播）；跨网段保留"手动指定地址加入"兜底，不扩大实现（落地接口见 2.1.10）。
- **2.1.5** **端口容错策略（合一条）**，消除 winNAT/WSL/被占导致的端口冲突：
    - **业务端口分两类处理**：
        - **对等通信 TCP（动态分配，可固定）**：监听默认绑定端口 0，由 OS 分配实际空闲端口，经 beacon 广播实际端口给对端（对端从广播读实际端口连接，不猜默认）；可配置固定端口 `peer_tcp_port`（默认 0=动态，2.14.3；预期被手动加入的节点应设固定值，2.1.10）。**push/pull 单次文件传输复用对等通信 TCP 通道，不单独立端口**（2.13.1 P2P 直传走同一 TCP 连接，分帧见附录 A）；**同步引擎 Syncthing 例外**——经其自有端口通信（2.4.7），两套机制不相混。
        - **面板 HTTP（固定默认 + 顺序兜底）**：默认固定端口（如 `5177`），被占则**顺序 +1 尝试**（5178、5179…），选到非默认端口时**弹非模态系统通知提示"默认面板端口被占用，已改用 XXXX"**（2.12.1，人类可理解）；实际面板 URL 写入 `data/panel.url`（2.14.1）供重开面板与 AI/技术人员查看（2.11.2）。面板**绑定 127.0.0.1（仅本机回环）访问**，无需广播。
    - **发现端口多端口冗余监听 + 广播全部端口**：节点同时监听一组发现端口，beacon 向所有发现端口广播；只要双方**至少一个共同空闲的发现端口**即可互通（某端口被占仅跳过该端口，不影响其余）。
    - **发现端口集分散在不同区间**（默认 `41830 / 41550 / 60420 / 31820 / 26880`，避免大块连续区间被占），可配置。**刻意避开 53317**（LocalSend 默认端口——本项目定位"加强版 LocalSend"，目标用户大概率同机装有 LocalSend，该端口高概率被占）。
    - **接收去重**：同一 beacon 从多个端口到达，按 `node_id + 序号` 去重。
    - **beacon 载荷携带监听端口列表**：广播发现靠盲听即可，手动定向加入（跨网段/手动指定 IP）时据此连接。
- **2.1.6** **节点在线状态检测**：beacon 超时 + TCP 主动探测，**无疑似态**：
    - 超时未收到某节点 beacon（可能是丢包或下线）→ 立即 TCP 探测该节点。
    - 探测成功 → 在线；探测失败 → **间隔重试，连续 3 次失败** → 判离线。
    - 面板节点状态仅 **在线 / 离线** 两态；每个节点各自维护"我看到的"对端状态（无中心权威）。
    - **默认时序参数**（可配；各节点实现必须一致，否则离线判定时序错配）：beacon 广播间隔 2s；连续 3 个周期（约 6s）未收到对端 beacon → 发起 TCP 探测；探测间隔 1s、连续 3 次失败 → 判离线。
    - **前端局部数据轮询**（间隔 3s）：只更新节点状态 DOM，**不整页刷新**（不打断选中文字/输入焦点），复用现有 FastAPI API。
- **2.1.7** **Team（可选隔离域，默认无）**：
    - **默认无 team**：节点默认无 team_id，与网络中任意节点连通（全放开基线）。
    - **team 是可选高级隔离**：仅当**面板设置**或**本机 AI 经 MCP 传入参数**（`set_team`）时给节点加 team_id。
    - **单 team**：节点同一时刻只属于一个 team（空=无 team；切换=换队）。
    - **隔离规则（彻底，作用于"是否连接/互通"而非"是否可见"）**：仅双方 team_id 一致才连通——有 team ↔ 无 team 也隔离；有 team X ↔ 有 team Y 隔离。**beacon 广播始终物理可见**（所有节点收得到、读得到 team_id/name/switches），隔离只影响"是否建立 TCP 连接/是否互通"，不影响"能否看到 beacon 信息"。
    - **切换即重发现**：改 team → 断开旧 team 连接/消息，重新发现新 team（同 team 才互通）；**原 team 节点经 beacon 可见其新 team_id，面板可明确显示"A 已切到 team Y"**（无需额外退队通知消息）。切 team 同时联动同步引擎：移除旧 team 节点的 Syncthing 设备与文件夹共享（2.4.7）。
    - **远程 AI 不能改他人 team**（如同不能改他人节点名称，2.1.3）；team 属"本机 AI 全权，与远程 AI 无关"。
- **2.1.8** **技术架构决策（已定）**：
    - **通信层**：点对点 TCP 明文，**全连接 mesh**（发现后与所有对端保持长连接，消息即时直达）。
    - **消息可靠性**：**fire-and-forget + 超时**（不设应用层 ACK，TCP 保证传输，超时判定，配合异步邮箱/日志可追溯）。
    - **消息模型**：TCP 投递到目标节点 → 目标节点落入本地 inbox 队列（调用方/AI 事后轮询取回，inbox 持久化见 2.6.8）。
    - **代码复用边界（分层复用，按功能语义，不依赖旧项目文件命名）**：数据模型（消息/对象定义）、节点发现、文件传输、配置加载等模块**保留功能并改造**；传输层**重写**为自研 P2P TCP（保留按 `correlation_id` 匹配请求/回执的逻辑）；本地存储用 SQLite（`comm.db`，2.14.1）；原 MQTT/中心桥接**删除**（2.14.2）。
    - **外部方案复用（方案 A，避免造轮子）**：**agent 间协作层采用 A2A 协议**（2.16.3，v1.0，SDK Apache-2.0，自研 TCP 作 custom binding）；**同步文件夹采用 Syncthing**（2.4.7，MPL-2.0，子进程 + REST 控制）；**执行器层（GUI 触发 + 弹窗可视化）自研**（无现成轮子）；CLAY 仅参考不复用（GPL + 中心架构不符）。
- **2.1.9** **已知节点持久化（离线不消失）**：
    - 曾发现/连上过的节点**持久化到本地 SQLite（复用 comm.db，2.14.1）**（known peers：node_id、name、team、能力、last_seen），beacon 在线时更新条目。
    - 节点离线后**仍显示为「离线 + 上次在线时间」，不消失**（面板节点列表 2.9.3/4.2；AI 经 MCP 可感知"某节点曾在线、现离线多久"）。
    - **清理**：提供「忘记节点」（面板/AI，MCP `forget_node`，2.5.9 ②）移除长期无用或已卸载的节点条目。
- **2.1.10** **手动指定节点加入（跨网段兜底落地，对应 2.1.4）**：
    - **配置**：`node_config.json` 新增 `manual_peers` 列表（如 `[{ "host": "192.168.1.50", "peer_tcp_port": 41840 }]`，2.14.3）——节点启动后对列表内地址**主动发起 TCP 连接**（不依赖 beacon），连接建立并经首帧校验（附录 A.1）后按正常 mesh 对等处理。
    - **被加入方需固定端口**：对等 TCP 默认动态分配（2.1.5），跨网段无法预知实际端口——预期被手动加入的节点应配置 `peer_tcp_port` 固定值。
    - **入口（能力对等映射 2.5.7）**：面板「设置」可增删 manual_peers；MCP 对应 `add_manual_peer(host, peer_tcp_port)` / `remove_manual_peer(host)`（2.5.9 ②）。
    - **范围限定**：手动加入仅打通发现/通信；Syncthing 同步依赖其自身局域网发现，跨网段同步不在保证范围（2.4.7）。

### 2.2 执行器（中间层 + 插件化 + 可见）
- **2.2.1** 执行器作为「调用其他电脑上智能体的中间架构」。
- **2.2.2** 执行器以**插件形式**存在，通过统一协议接口与节点通信（**统一接口定稿见 2.2.15**）；插件可随时增加对任意品牌智能体支持。
- **2.2.3** 插件同时支持 **GUI 智能体** 与 **CLI 智能体**。
- **2.2.4** **CLI 智能体被调用时（含非交互调用）必须在目标机显式弹窗**，显示主智能体发的消息与被调智能体的回复。CLI 走可见终端窗口（psmux/tmux `attach_visible`）。
- **2.2.5** **GUI 智能体不弹黑窗口**——其输出出现在它**自己应用的窗口**里（可见即可观），不强行弹终端。**GUI 可见深度定为 A**：界面可见 + 能注入任务运行 + 回传结果；不强行逐字搬回纯文本输出（GUI 通常无纯文本流）。
- **2.2.6** 非交互执行器**默认即可视化（标准模式）**：在独立 detached 会话中运行 + attach_visible 弹窗，窗口独立，非交互也可见；且不依赖执行器宿主终端存在（服务/后台下仍成立）。**可见体验**：弹窗中显示拉起 CLI 的命令、注入的提示词参数、CLI 智能体的实时输出；**仅 CLI 非交互执行器**任务完成后**停留片刻（几秒）再关闭**（让人看完输出，否则"可见"打折扣），随后进程退出弹窗关闭——**GUI 执行器不适用此停留**（其完成任务即关窗口，见 2.2.11 适配器实现）。**弹窗边界（无"主动隐藏"参数）**：有桌面会话 → 弹窗可见（attach_visible 成功）；**无桌面会话（如 Linux 服务器/SSH，无 DISPLAY）→ attach_visible 自动降级为 headless 不弹**（无图形终端可 attach），但 CLI 智能体照常运行、结果经**结果文件契约**（2.2.11）取回——"隐藏"是无桌面环境的客观限制，非用户选项。
- **2.2.7** **自动发现 + 显示节点自定义名称**：节点启动即自动广播/扫描局域网对等节点（beacon 无主从）；beacon 载荷携带节点显示名，因此**自动发现到其他节点时即显示其自定义名称**，无需手动配置。
- **2.2.8** **复用已有 GUI 执行器注入回收核心为插件素材**：WorkBuddy（deeplink + UIA 注入/回收）、TraeWork（CDP 注入 + 结果文件契约/DOM 回收）两个已开发执行器的**注入/回收核心逻辑原样保留**，作为重构后插件协议的现成实现体；仅替换其总线耦合层（原中心总线/MQTT 耦合 → **A2A 协议端点（2.16.3，执行器作为 A2A Server）** + 节点本地通信）。
- **2.2.9** **执行器进程模型 = 混合 + 并发度**：**交互式 TUI 执行器常驻 daemon**（保 TUI 会话跨任务复用；并发度默认 1，可配 >1 = 多独立常驻会话并行，2.13.2）；**非交互 CLI 执行器按需唤起**（每次任务新进程/新会话，更新即生效；并发度默认 3 可配，在途 ≥ 并发度 → 拒绝）；**GUI 智能体执行器常驻 daemon**（需持续追踪 GUI 窗口/会话——WorkBuddy 窗口、TraeWork 会话；并发度固定 1，匹配 2.13.2 交互式排队）。**并发隔离**：每任务独立工作目录 `data/executor_work/<agent_id>/<task_id>/`（2.2.11），并发实例互不干扰。**【v1 暂缓】**：交互式 TUI 的**跨任务会话上下文复用与并发度 >1（多会话并发）暂缓实现**（后续版本，2.2.16）；v1 交互式只做最简——单常驻会话、任务串行排队（2.13.2）。**非交互 CLI 并发（默认 3）v1 即支持**。
- **2.2.10** **远程分发执行器插件（新增 + 更新，合并一条）**：智能体/人类可向所有 `allow_file` 打开的节点 push 执行器插件文件。**插件分发 = 文件写操作 + 进程管理操作的组合，非独立能力，受 `allow_file` 开关管辖**；`allow_file` 关闭时自动拒绝，无需单独开关：
    - **新增插件**：push 新插件文件到各节点插件目录 → 节点重扫插件目录/重启后自动发现并纳入能力广播（无需手动配置）。
    - **更新插件**：push 新版本文件覆盖 → 非交互执行器按需唤起即生效；交互式执行器需**重启该插件进程**才生效（会话常驻）。
    - 更新结果回执给发起方，并记入双方本地通信日志。
    - **AI 一键分发 = MCP 工具 `distribute_plugin(target_node, plugin_path)`（2.5.9）**：AI 侧一个语义操作即完成整套编排（file_push 到 `data/plugins/` + `plugin_sync` 触发目标节点重扫/交互式执行器重启（2.16.4）+ 回执 + 记双方日志），**不要求 AI 自己拼 `file_push` + `restart_plugin`**。
- **2.2.11** **统一插件接口（签名见 2.2.15）+ 结果文件契约（统一取回）**：
    - **统一接口（2.2.15 定稿）**：所有执行器（GUI / 交互式 TUI / 非交互 CLI）共用 `submit / is_done / get_result / status` + 生命周期；各品牌实现为**适配器**（WorkBuddy=deeplink+UIA，TraeWork=CDP；其内部 `submit` 即注入 `inject`），对统一接口负责，新品牌仅写一个适配器。**首批适配器 = workbuddy + traework 两个**（复用现成注入回收核心）。旧 `start/stream/cancel/status`（交互式）与 `inject/poll_reply/is_done`（GUI）两套接口**废止**，统一为 2.2.15。
    - **结果文件契约 = 所有执行器类型的统一取回机制**：提示词要求被调智能体把最终结论写入**指定结果文件**——位于**该任务自己的工作目录**（`data/executor_work/<agent_id>/<task_id>/`，按任务隔离、并发安全，2.2.9），结果文件名固定（`result.md`，目录即任务标识）。**GUI 必须**（无法可靠解析窗口文本）；**CLI/TUI 也用**（避免逐品牌解析终端输出不稳定，2.2.6 无桌面降级同此）。
    - **提示词要求原子化写入**：先写 `.tmp` 临时文件再 rename 成最终名（`result.md`）。
    - **`is_done()` 判定**：最终名文件存在 + 大小稳定（连续 N 轮不变）+ 超时兜底，防"写入中提前返回"；临时文件/写入中的变化不算完成。
- **2.2.12** **执行器能力自检 + 能力广播依据**：执行器**启动时**探测本机是否具备对应智能体应用——CLI 用 `which`（查可执行文件），GUI 查窗口（UIA）/CDP 端口；**以"启动时能否探测到"为准决定是否广播能力**（探测到 → 广播该能力；探测不到 → 不广播，能力列表只显示当前确实可用的）。探测不到 → **拒绝接收任务**（日志 + 回执给请求方明确错误"未检测到 XXX 应用"）。GUI 智能体**已安装但未运行时 → 拒绝并提示"请先在目标机启动 XXX 应用"**（由人类保证 GUI 已运行，执行器不自动冷启动拉起）。
- **2.2.13** **执行器前提条件披露（三层）**：
    - **每执行器自带说明书文件**（插件目录/源码内）：详细前提条件与配置步骤（如 TraeWork 需在 `argv.json` 开启 `remote-debugging-port: 9433`、WorkBuddy 需普通权限），为**单一事实来源**；AI 经 skill（2.5.4）或 MCP 工具 docstring 读到。（另含**会话策略**——fresh 型/会话型，2.2.16；与**并发度**——2.2.9，供 AI 选择执行器。）
    - **面板"执行器"栏位展示前提摘要**：人类在面板能看到每个执行器的"前提条件"提示（人类自查主渠道）。
    - **报错联动**：失败（2.13.5）时错误信息附带前提条件提示（如"TraeWork 需开启 CDP 端口 9433"），供使用时的即时排查。
- **2.2.14** **交互式执行器授权/登录处理**：
    - **授权请求（trust 对话框等）自动通过**：执行器启动时自动检测并匹配授权对话框（trust 确认等），自动注入按键（如 Enter），**不打扰人类**。
    - **登录请求检测（尽力识别，降预期）**：经 profile 匹配**能识别**的登录界面（如需要输入账号）→ 判定 `auth_required`，回执返回"目标 CLI 需要登录，请到该机器查看 psmux 窗口并登录"；**识别不到**的登录界面 → 不强行判定，走超时兜底（2.13.5）+ 窗口置顶提示（至少人类能看到窗口）。
    - **窗口置顶/通知提醒**：检测到登录请求（或长时间无进展疑似卡在登录）时**确保 psmux 窗口置顶/前台**，并**弹非模态系统通知（2.12.1）提醒人类**"该节点 CLI 可能需要登录，请查看窗口"——因 AI 没有眼睛，窗口不在前台可能人类也注意不到。**置顶实现归属**：psmux/tmux 的 attach 只负责开窗、不保证置顶——置顶/前台由**节点核心用平台 API 实现**（Windows `SetForegroundWindow`；Linux `wmctrl`/`xdotool`，2.15.3），不依赖终端复用器。
- **2.2.15** **执行器插件接口（定稿签名，AI 施工硬契约）**：
    - **统一接口原则**：**一套接口覆盖 GUI / 交互式 TUI / 非交互 CLI 三种类型**；类型差异（驱动窗口 / 注入会话 / spawn 可见窗口）只在各适配器内部实现。可见性由真实窗口承担（2.2.4/2.2.5），结果统一由结果文件取回（2.2.11），**不设 `stream` 接口方法**（可见=窗口，取回=文件）。挂起/恢复是**节点核心级门控**（4.3），**不属插件接口**（节点核心拒绝调度即可）；**插件 `status()` 只上报 `idle/busy`，`suspended` 由节点核心叠加呈现**（对外/面板/协议，2.9.10/4.3）。
    - **契约边界**：**绑定（MUST）**——方法名、参数名、字段名、数据类型、返回语义（以下签名为准）；**自由（施工定）**——具体类/文件组织（dataclass/dict/ABC 皆可）、内部实现、各品牌适配器如何驱动窗口/会话/CLI 进程。**插件语言 = Python**（节点核心为 Python，2.11.1）。
    - **标识符层级（消除歧义）**：`plugin_id`（品牌插件标识，如 `workbuddy` / `codebuddy-cli`）→ `agent_id`（**执行器条目在本节点的标识**：同品牌多条目时含变体，如 `codebuddy-cli` / `codebuddy-tui`；即 `PluginContext.agent_id`，也是工作目录隔离键与 `plugin_sync` 的目标键）→ `executor_id`（**全局寻址** = `<node_id>/<agent_id>`，2.5.9）。节点核心收到 `executor_id` 后分解为 (node_id, agent_id) 再路由。**勿混淆**：`agent_id` 是执行器**条目**标识——不是被调用的智能体本身、不是调用方身份（调用方 = `caller_id`，2.6）、也不是 A2A 泛指的 agent；SKILL 中须保留此辨析（2.5.3）。
    - **签名（规范契约，非示意伪代码）**：
        ```python
        class PluginContext:
            node_id: str
            agent_id: str          # 工作目录隔离键（executor_work/<agent_id>/<task_id>/，2.2.9）
            work_dir: Path
            config: dict           # 插件配置（含授权对话框匹配等启动参数，2.2.14）

        class CapabilityResult:    # 启动自检（2.2.12）
            available: bool        # CLI=which；GUI=窗口/CDP 探测
            reason: str | None     # 不可用原因
            premises: list[str]    # 前提条件摘要（2.2.13）

        class TaskInput:           # 对齐 A2A Task（2.16.3）；不含 mode（执行器不感知 sync/async/trigger，2.7.5）
            task_id: str
            prompt: str            # 含"把最终结论写入结果文件"指令
            attachments: list[str] # 已 P2P 直传到 work_dir（2.13.1）
            result_file: Path
            timeout: float

        class SubmitResult:
            ok: bool
            error: ErrorCode | None   # offline/disabled/suspended 由节点核心产生（远程路由/门控）；插件本地仅产生 not_installed/busy/timeout/agent_error（2.13.5）
            detail: str | None

        class ExecutorStatus:      # 面板 / executor_status 协议（2.9.10）
            available: bool
            state: Literal["idle","busy","suspended"]  # 插件只报 idle/busy；suspended 由节点核心叠加（2.9.10）
            inflight: int          # 在途任务数（2.13.2）
            concurrency: int       # 并发度上限（2.2.9）
            current_task: str | None
            queue_len: int         # 排队型（TUI/GUI）队列长度；非交互 CLI 忙时拒绝不排队、恒为 0（2.13.2）
            until: datetime | None # 挂起到期时间点（4.3）

        class ResultPayload:
            ok: bool
            error: ErrorCode | None
            content: str | None    # 结果文件内容（成功时）

        class ExecutorPlugin(ABC):
            plugin_id: str
            display_name: str       # 品牌默认显示名；条目可被用户/AI 改名（rename_executor，2.5.9 ⑦），改名后以 name 为准
            executor_type: Literal["interactive_tui","non_interactive_cli","gui"]
            concurrency: int        # 并发度上限：GUI=1；非交互 CLI=默认 3 可配；交互式 TUI=默认 1（>1 为后续版本，v1 暂缓，2.2.9/2.13.2）
            # 生命周期
            def on_load(self, ctx: PluginContext): ...
            def on_unload(self): ...
            def check_capability(self) -> CapabilityResult: ...
            # 任务
            def submit(self, task: TaskInput) -> SubmitResult: ...
            def is_done(self, task_id: str) -> bool: ...
            def get_result(self, task_id: str) -> ResultPayload: ...
            # 状态
            def status(self) -> ExecutorStatus: ...
        ```
    - **注册表（`executors/registry.py`，2.14.1）**：`load_plugins(plugins_dir)` 扫描 `data/plugins/` 实例化插件 → 逐个 `check_capability()` → 可用者纳入能力广播（2.2.12，Agent Card，2.16.3）→ 节点核心把 `executor_id` 分解为 (node_id, agent_id) 后路由到本节点对应条目（2.5.9/2.9.10）。`data/plugins/` 新文件被分发后（2.2.10）重扫即纳入。
    - **数据模型对齐 A2A**：`task_id` 即 A2A Task id；Task 生命周期状态机（submitted/working/completed/failed…）由**执行器包装层**实现（2.16.3），复用 a2a-sdk 类型（Task/Message/Part/Artifact）；插件接口以任务对象交互，不暴露裸 A2A 传输（自定义 TCP binding，2.16.1）。
    - **任务语义对齐（mode 归属）**：**执行器不感知 sync/async/trigger**（2.7.5）——`TaskInput` 不携带 mode；三种模式是**调用侧/节点核心语义**（是否阻塞、是否取回执、触发确认 2.7.1），由节点核心据调用方的请求记录并按需处理回执；执行器统一"收到即运行 + 结果写入 `result_file`（2.2.11）"。触发型任务的"触发确认"由节点核心在 `submit` 返回 `ok` 后给出（2.7.1），执行器无特殊分支。
- **2.2.16** **会话策略 = 执行器层管理（类型即策略，不丢给 AI）**：
    - **非交互 CLI（v1 实现）**：每次任务 = **全新会话**（fresh），进程退出即结束 → **无跨任务历史**（AI 选它 = 一次性全新任务）。
    - **交互式 TUI（v1 最简，语义定死）**：单常驻会话、任务串行排队（2.13.2）。会话上下文是否跨任务累积由 CLI 智能体自身行为决定（节点不干预、不清空）；**"暂不复用"指节点不提供会话管理接口**（不新建/不续接/不指定会话，属 2.2.9 v1 暂缓项）。
    - **交互式 TUI（后续版本）**：**跨任务上下文复用**（单会话延续）与**并发度 >1**（多独立常驻会话、任务分发给空闲会话、会话内串行，2.13.2）——**v1 暂缓**（2.2.9）。
    - **AI 的接口**：AI 只经 `list_executors` / 前提披露（2.2.13）获知每个执行器的**会话策略**（fresh 型 / 会话型）与**并发度**，据此选择执行器；**不传会话参数、不管理会话**（2.5.8 透明路由、极简）。**会话策略由 `executor_type` 推导**：`non_interactive_cli` = fresh（每次新会话）；`interactive_tui` / `gui` = session（常驻会话）。
    - **可选显式覆盖（留施工、默认不做）**：如将来需要"同一执行器上显式新建/续接指定会话"，再给 `submit_task` 加可选参数（`session: new | resume`），当前不加。
    - **历史清理（执行器层管）**：每任务目录任务完成后按保留策略清理（保留最近 N 个供查）；交互式常驻会话历史由 CLI 自身持久化，执行器只管理任务目录生命周期，不干预其内部文件。

### 2.3 通信日志
- **2.3.1** **每节点本地独立日志**：每个节点自持本地通信日志（SQLite）；自己发出 + 自己收到全量落盘；调/被调双方各自可见自己的本地日志；不提供跨节点拉取他人日志（简化）。
- **2.3.2** 通过 MCP，本机 AI 可查本机通信日志。

### 2.4 文件控制面（统一 push/pull，含远程文件浏览器）
- **2.4.1** 节点控制面可**向其他电脑发送文件**（push）或**从其他电脑拉取文件**（pull）；push/pull **统一为同一组底层原语，目标路径均可指定**。
- **2.4.2** **push 目标路径可指定任意绝对路径**；**默认值为统一收件目录**（统一名 + 节点无关，如 `data/inbox/`，固定路径、节点名无关、易定位，**ASCII 命名**），不指定时落到该目录。
- **2.4.3** **pull 允许指定对方任意绝对路径**（读全放开，如 `/data/docs/report.md` 或 `D:\report.docx` 这类任意位置亦可拉取，不绑定特定用户目录）；拉取到本机**统一收件目录**（默认）。
- **2.4.4** **`list_dir` 目录浏览能力必要**：可列出目标节点某目录内容（支持递归模式），配合 pull/push 任意路径使用。
- **2.4.5** 每次文件操作同样记入双方各自的本地通信日志。

**原子化拆解（Given/When/Then）：**
- **2.4.G1** Given 人类在面板打开某节点文件浏览器，When 点击某目录，Then 显示该目录内容（可递归展开，进入子目录/返回上级）。
- **2.4.G2** Given 人类在面板选择远程某文件夹并点击下载，When 发起下载，Then 目标机递归返回整树文件清单，逐文件传输到本机并按原路径重建目录树（不经打包）。
- **2.4.G3** Given 人类在面板浏览到目标目录并选择本机文件上传，When 发起上传，Then 文件被 push 到该目录（未指定则落对方统一收件目录）。
- **2.4.G4** Given AI 通过 MCP 发送文件且未指定目标路径，When 调用发送，Then 文件默认落到对方统一收件目录。

- **2.4.6** **远程文件浏览器（Web 面板，统一文件操作的人类入口）**：
    - 人类可在 Web 面板浏览其他节点的文件目录结构：从目标机器**文件系统根目录**（平台根：Windows `C:\`、Linux/macOS `/`）开始，支持进入子目录、返回上级。
    - 面板内下载到本机：单文件直接下载；**文件夹整目录复制下载、不经打包**——递归列出目录树全部文件清单，逐文件传输，本地按原路径重建目录树（无 zip、不占对方临时空间）。
    - 面板内上传 = push 到当前浏览目录：在目标目录内选择本机文件上传，即 push 到该任意路径；不指定目录时默认落到统一收件目录。上传与 AI 发文件是同一操作、不同入口。
    - 文件浏览器复用 `list_dir`（递归）/ `pull` / `push` 既有原语，不新增协议；所有浏览/下载/上传均记入双方本地通信日志。
- **2.4.7** **同步文件夹（分布式云空间，防损 + 共享，基于 Syncthing）**：
    - **复用 Syncthing（MPL-2.0）**：同步引擎**采用 Syncthing 作为节点子进程**（静态附带 `syncthing` 二进制，随包分发），节点经其 **REST API**（`/rest/config/folders`、`/rest/db/scan`、`/rest/events` 等）编程控制——复用其成熟的增量同步/冲突处理/传输，不自研同步引擎。
    - **设备配对与共享引导（自动互配）**：Syncthing 以设备证书指纹（device ID）互认，双方互加对方 device ID 并共享文件夹才能同步——引导流程定死如下：
        - **device ID 经 beacon 交换**：beacon 载荷新增 `sync_device_id` 字段（2.16.2；本机 Syncthing 子进程首次启动时生成证书，节点读取其 device ID；同步关闭的节点该字段为空、不参与互配）。
        - **同 team 在线对端自动互配**：收到同 team 对端 beacon（含 `sync_device_id`）→ 经 REST API 自动添加对方为 Syncthing 设备 + 共享 `data/sync/` 文件夹（**对称执行**，双方互加即连通）。
        - **team 隔离联动**：team 不一致的对端**不添加**其设备；切换 team 时移除旧 team 节点的设备与共享（2.1.7）。
        - **范围**：依赖 Syncthing 自身局域网发现；跨网段同步不在保证范围（2.1.10）。
    - **统一同步目录**：所有节点同一相对路径同一名称（如 `data/sync/`，**ASCII 命名**）；**默认开启**，可面板/MCP 配置关闭（经 REST 配置文件夹）。
    - **对称**：任何节点可发起；无主源（Syncthing 本身对等）。
    - **同名冲突：最后写入覆盖**（Syncthing 默认策略，不做额外版本库）。
    - **默认非周期/事件驱动**：Syncthing 自带实时文件监听；提供触发接口（MCP `sync_now()` + CLI `cli.py sync` 经 REST `/rest/db/scan`，供 AI/脚本调用）；计划任务（schtasks/cron 定期调用）由用户自行实现。
    - **普通 P2P 单次传文件仍走原 push 接口**（2.4.1/2.4.2）；同步目录是独立机制（Syncthing 专有），两不相混。
    - **许可合规**：作为独立子进程调用 + REST 控制，不构成衍生作品（MPL-2.0 弱 copyleft），分发时保留 Syncthing 许可声明。

### 2.5 智能体接入（MCP + CLI 双入口 + 配套 Skill）
- **2.5.1** **双接入方式，能力等价**：
    - MCP Server：供支持 MCP 的智能体（AI 客户端）连接，暴露节点能力为 MCP 工具；**薄转发桥**——由 AI 以 stdio 拉起（2.6.3），仅参数校验/语义组装/结果回传，**实际执行在节点核心进程**（宿主权限，2.10.4）。
    - CLI 工具（`cli.py`）：供**不支持 MCP、但有 Bash/终端能力**的智能体调用（**语义化子命令**：`register / list / send / task / check / inbox / upload / download / ls / shell / node-update / sync / diag / executors`，2.5.8）。
- **2.5.2** **工具级说明内嵌 MCP docstring**：每个 MCP 工具自带参数/用途说明，供 AI 按需读取调用。
- **2.5.3** **配套一个 Skill 说明书（`SKILL.md`）**：统一讲解节点协作协议、双接入方式、命令参考、示例工作流与配置加载。**必须放在项目最后再写**——因架构/接口变更会影响其内容，待架构与接口稳定后再落笔，避免反复改动。
- **2.5.4** **Skill 披露分层**：Skill 内包含**全部能力描述 + 常用命令/脚本说明**；更复杂的功能说明、架构文档、完整说明书**放 skill 之外的其他文件**，AI 按需读取（本机 AI 亦可直接读源码兜底）。（**深文档另有门控**——完整架构 + 协议接口标准仅重大故障排查用，默认不暴露、经人类允许开放，见 2.17.7。）
- **2.5.5** **Skill 必须包含 mihomo/网络排查指引**：因许多用户不懂代理，而 AI 可感知本机网卡/IP 异常（`ipconfig`/`ip addr`、路由表、beacon 收不到对端等），Skill 须写入 **mihomo 配置指引（2.18.2）+ 排查流程**：AI 检测到"局域网互连失败但本机网络正常"→ 判断可能 TUN 代理未配局域网直连 → 读 Skill 给人类配置指引（2.18 关联）。
- **2.5.6** **AI 与节点程序的边界**：Skill 明确四层——
    - **允许**：AI 通过**标准接口**影响节点进程（重启插件、远程分发插件 2.2.10、经 MCP 控制节点状态等正规通道）。
    - **禁止**：AI 修改任何**源码 / 打补丁 / 改配置文件**（文档约束，**不做技术设防**——MCP 工具层路径过滤无意义，因有 MCP 的智能体同样有 `run_command`，可绕过滤；执行器驱动的智能体本身就是完整权限程序，节点侧无法技术阻止）。擅自改动会导致节点逻辑变化而其他节点不知情，破坏协同一致性。
    - **允许**：AI **读取/探测**节点进程运行状况（状态、日志等，经 MCP 查看工具）。
    - **禁止**：AI **擅自启动 / 停止 / 重启节点进程**——节点进程生命周期由**人类掌控**（2.9.6 面板不杀进程、2.11.3 单实例、2.12.2 人类重启）；AI 可探测节点运行状态并诊断（2.17.7），异常时给人类重启指引，**不自行 kill/重启节点进程**（会中断本机与远程连接、影响其他客户端、可能丢未持久化状态）。此为**文档约束、不技术设防**（AI 有 `run_command` 技术上可做，但属行为规范）。
- **2.5.7** **能力对等映射（硬性需求）**：每个面板可见项须有对应 MCP 查看工具，每个面板可操作项须有对应 MCP 操作工具（本机 AI 全权）；远程 AI 的查看/操作均通过节点通信协议实现，受对应开关（2.9.4）管辖。
- **2.5.8** **AI 调用 = 统一语义化接口（本地/远程透明路由，省 token 防出错）**：
    - **统一调用面**：AI 经 MCP 调用执行器，**本地与远程执行器用同一工具签名**（如 `submit_task(target_executor, prompt, mode=sync|async|trigger, ...)`），由**节点核心透明路由**——本地走进程内 A2A Server（2.16.3），远程走 P2P TCP（A2A 任务封装）；**AI 无需感知目标在本机还是远程**。差异仅在底层：远程需目标在线 + 受 `allow_ai_task` 管辖，失败返回 `offline`/`disabled` 等错误码（2.13.5）。
    - **语义化接口原则**：AI 的主接口是 **MCP 工具**（结构化命名参数、无 shell 转义、无长命令行、不拼裸协议报文）——一个工具 = 一个语义操作，避免超长命令不稳定/出错/浪费 token；**不向 AI 暴露裸协议报文构造**。cli.py 为**非 MCP 智能体的次接口**，用**语义化子命令 + 短标志**（如 `cli.py task --target <node> --executor <id> --prompt "..." --mode async`），同样避免超长命令/裸 JSON。
    - **暴露给 AI 的执行器相关工具（本机，2.5.7）**：完整工具清单见 **2.5.9 MCP 工具面**（`list_executors` / `submit_task` / `get_task_result` / `check_mail` / `get_executor_status` / `set_executor_suspend` 等）。
- **2.5.9** **MCP 工具面（定稿清单，本机 AI 全权）**：
    - **原则**：工具面 = 本机 AI 经 MCP 感知/操作的全部工具；**语义化**（2.5.8：一个工具 = 一个语义操作、命名参数、不拼裸报文）；**能力对等映射**（2.5.7：面板可见项→查看工具、可操作项→操作工具）；**寻址用 node_id**（2.14.3）；跨节点工具受对应开关（2.9.4）管辖，失败统一返回 2.13.5 错误码。**`set_*` 仅作用于本节点**（改名 2.1.3 / team 2.1.7 / 开关 2.9.5 / 挂起 4.3，远程不可改）。**寻址分工**：执行器级操作传 `executor_id`（格式 `<node_id>/<agent_id>`，全局唯一、内含归属节点，由 `list_executors` 返回，AI 无需另传 node_id，2.2.15 标识符层级）；节点级操作传 `node_id`（2.14.3，如 send_text / 文件 / shell_exec）。**命名统一**：节点寻址标识一律为 `node_id`——MCP 参数名 `target_node` 的取值即目标节点的 node_id，协议信封字段为 `target_node_id`（附录 A.3），同义同值、禁止第三种叫法（协议旧称 `target_id` 废止）。
    - **① 本机状态（概览视图）**：`get_node_info()` — 本机 node_id、名称、team_id、IP、运行时长、发现端口、面板 URL、三开关状态、在线状态
    - **② 节点（节点视图，2.1.9）**：`list_nodes()` — 已知节点列表（含离线不消失：node_id + 名称 + team + 能力 + 在线/离线[last_seen]）；`forget_node(node_id)` — 忘记节点；`add_manual_peer(host, peer_tcp_port)` / `remove_manual_peer(host)` — 手动指定节点加入/移除（2.1.10，跨网段兜底）
    - **③ 聊天（消息视图，2.8.8，不受开关）**：`send_text(target_node, text, session_id?)` — 发文本（仅在线可发）；`list_conversations()` — 会话列表；`get_chat_history(target_node, limit?)` — 聊天记录（仅本节点为一方）
    - **④ 文件（文件视图，2.4，受 allow_file）**：`list_dir(node_id, path, recursive?)` — 列远程目录；`file_push(node_id, local_path, target_path?)` — 推送到任意路径（默认统一收件目录）；`file_pull(node_id, path)` — 拉取到本机收件目录；`sync_now()` — 触发同步（2.4.7）；`list_plugins()` — **仅列 `data/plugins/` 磁盘插件文件**（词汇边界：插件=磁盘上的包；加载后的运行实例与深态见 ⑤ `list_executors`）；`distribute_plugin(target_node, plugin_path)` — 分发/更新执行器插件（2.2.10：内部编排 = 推送文件到 `data/plugins/` + 触发重扫/交互式执行器重启 + 回执 + 记双方日志，受 allow_file）
    - **⑤ 执行器（执行器视图，2.2.15/2.9.10，远程任务受 allow_ai_task）**：`list_executors()` — 本机+远程统一枚举（每执行器返回唯一 `executor_id` + 归属 node_id + `name`（可改名，指称用）+ 能力（含**会话策略**/并发度，2.2.16/2.2.9）+ 在线 + 前提摘要；**本机含完整状态[空闲/忙碌/挂起含原因到期/在途/并发度]，远程仅 beacon 可得的在线/能力，默认不深度查**，2.9.3）；`submit_task(executor_id, prompt, mode=sync|async|trigger, attachments?, timeout?, task_id?)` — 统一调用（executor_id 内含归属节点，由 list_executors 返回，AI 无需另传 node_id；透明路由本地/远程）；`task_id` 可选**幂等键**——调用者重试时复用同一 task_id，目标节点据此幂等、不重复执行（2.13.5）；`get_task_result(task_id)` — 同步取结果；`check_mail()` — 异步邮箱取回执（caller_id 自动注入，2.6）；`get_executor_status(executor_id)` — 读执行器深态（本机直接；**远程按需深查**，经 `executor_status` 协议、受 allow_ai_task，2.16.4；含挂起/原因/到期，4.3）；`set_executor_suspend(executor_id, suspend: bool, reason?, until?)` — 挂起/恢复（本机，4.3）；`restart_plugin(executor_id)` — 重启插件（**仅本机**，4.3 面板操作 / 2.2.10 更新生效；远程插件更新生效经 `distribute_plugin` 内部编排 `plugin_sync`，2.16.4）；`list_agent_sessions(executor_id?)` — 交互式会话列表（本机直接；**远程按需深查**，经 `executor_status` 协议、受 allow_ai_task，2.16.4）
    - **⑥ 日志（日志视图，2.3/2.9.7）**：`get_comm_log(target_node?, direction?, type?, correlation_id?, limit?)` — 通信日志；`get_node_log(source=node|mcp|executor|syncthing, lines?, level?)` — 节点相关程序运行日志（node.log 默认；排查时全量可感知，2.17.7）
    - **⑦ 设置（设置视图，本机配置）**：`get_config()` — 读本机配置；`rename_node(new_name)` — 节点改名（2.1.3）；`rename_executor(executor_id, new_name)` — **执行器改名**（本机，2.2.15；AI 用 name 指称、executor_id 寻址，远程不可改）；`set_team(team_id)` — 设置/切换 team（2.1.7，危险操作）；`set_control_state(switch, enabled)` — 三开关（2.9.5）；`set_run_as_admin(enabled)` — 权限（2.14.6，需重启生效）；`cleanup_mail(mode=consumed|expired, before?)` — 清理已读/超期未读（2.6.9）
    - **⑧ 远程命令（shell_exec，2.16.4，无面板视图，受目标节点 allow_shell）**：`shell_exec(target_node, command, timeout?)` — **本机节点作为转发网关，执行在节点核心进程**（2.10.4）：`target_node`=本机 → 本机直接执行（本机 AI 全权，不受开关，2.9.4）；`target_node`=远程 → 本机节点经 P2P TCP 转发 `shell_exec` 报文，受**目标节点** `allow_shell` 管辖（2.9.4），返回 `shell_result`。AI 无需自己拼报文（2.5.8），本机 AI 亦可走原生 `run_command`（2.10.3，不经节点、不入 comm 日志）
    - **不在工具面（无需或另有通道）**：裸协议报文构造——禁止（2.5.8，一切远程能力经 ①~⑧ 语义工具）。

**原子化拆解（Given/When/Then）：**
- **2.5.G1** Given 某智能体不支持 MCP，When 它想参与节点协作，Then 可通过 Bash 调用 `cli.py` 子命令完成注册/发现/发任务/回传，与 MCP 智能体能力等价。
- **2.5.G2** Given 智能体使用节点能力前，When 其加载配套 Skill 说明书，Then 获得完整的协作协议与用法（含两种接入方式），而 MCP 工具级说明仅提供单工具的即时用法。

### 2.6 异步消息与 caller_id
- **2.6.1** **需要真异步**：A 的智能体发任务给 B 后**不阻塞**，A 继续干别的事；B 完成后结果稍后回执。
- **2.6.2** **节点级身份 + 调用者级归属分离**：线上寻址以**节点**为单位（任务经 A2A 端点发往目标节点的执行器，2.16.3；聊天经自研 text_request 发往目标节点，2.16.4）；异步回执归属按**调用者（caller_id）**在节点内解复用，避免同一节点多个 AI 客户端互相看到对方回执。
- **2.6.3** **caller_id 实现 = MCP server 进程身份**：一个 MCP server 子进程 = 一个智能体客户端（由该智能体以 stdio 子进程方式拉起）；caller_id 即该进程身份，随每个工具调用自动注入，**智能体无需在自身上下文记住 id**。
- **2.6.4** **caller_id 获取（MCP 自动派生，无需配置）**：MCP server 由客户端以 stdio 子进程拉起，启动时读取**父进程可执行名**（workbuddy.exe/trae.exe…）归一化派生为 caller_id——同一客户端重启后 id 不变、不同客户端 id 不同、本机不冲突（caller_id 只需节点内唯一，跨电脑重复无影响）；父进程探测失败时退回每进程临时 UUID（绝不撞号，代价是跨重启找回不了旧回执）。**用户无需配置任何 caller id。**
- **2.6.5** **节点内按 caller 解复用**：异步任务登记 `pending[caller_id][correlation_id]`；B 的回执按 `correlation_id` 反查归属 caller_id → 放入该 caller 私有队列；`check_mail(caller_id=...)` 只返回自己的结果。
- **2.6.6** **CLI 智能体的 caller_id**：CLI 为一次性进程、无常驻 MCP server 帮注入 id，因此从身份文件（`~/.config/agent-node/caller.json`，`cli.py register` 生成）读取，亦可用环境变量 `AGENT_NODE_CALLER_ID` 覆盖；异步对 MCP 与 CLI 均开放。
- **2.6.7** **SKILL 必须明确写明「caller_id 对应自己的邮箱」**：该映射是核心认知，须在 SKILL 中明确，任何智能体加载 SKILL 时都会读到，确保所有智能体都清楚自己的 id 与专属邮箱的对应关系。
- **2.6.8** **mailbox 持久化**：节点异步邮箱（`mailbox`，SQLite `mailbox` 表）**落盘到本地 SQLite（复用通信日志库）**，加"已消费"标记字段（consumed: 0/1）；所有入箱回执落库（consumed=0），`check_mail` 取走时标记 consumed=1，节点重启后从库恢复未消费消息（**去中心化后无中心兜底，必须落盘防重启丢失**）。通信日志保留全量历史（审计），与 mailbox 视图同库区分。**命名：`mailbox`（异步邮箱）与"文件收件箱"（`data/inbox/` 目录）严格区分，二者互不相干。**
- **2.6.9** **已读语义与积压策略**：`check_mail` **取走即标已读**（consumed=1），已读消息不再出现在 mailbox 查询（保留在通信日志做审计）；**未读邮件默认长期保留**（属审计一部分），提供**清理机制**（面板/AI 可清理已读或超期未读），防无限膨胀且不误删。

**原子化拆解（Given/When/Then）：**
- **2.6.G1** Given 节点 A 上多个 AI 客户端各自连接独立 MCP server 进程（各持 caller_id），When 其中某客户端发起异步任务且 B 回执到达，Then 回执按 correlation_id 归属到对应 caller_id 的私有队列，其他客户端看不到。
- **2.6.G2** Given MCP server 子进程重启，When 其身份文件/环境变量未变，Then caller_id 不变，历史异步回执仍可被该客户端找回。
- **2.6.G3** Given 任一智能体加载 SKILL 说明书，When 其查询「我的收件箱 / 我的 id」，Then 能从 SKILL 明确获知 caller_id 与专属收件箱的对应关系。

### 2.7 消息模式（文本 / 同步任务 / 异步任务 / 触发型）
- **2.7.1** **消息模式分类**（文本消息 + 三种任务）：
    - **文本消息**（替人类发给别的节点）：只要求**到达对方节点**，进聊天通道，不等待。
    - **同步任务**：经执行器唤醒目标智能体（任务经 **A2A 协议**发往目标节点的执行器端点，2.16.3），调用侧**阻塞**等回执。
    - **异步任务**：经执行器唤醒目标智能体，调用侧**不阻塞**，继续干别的；执行器读取回复后，回执返回到**调用者节点的异步邮箱**，调用者事后 `check_mail` 取。
    - **触发型任务**：发送仅唤醒目标智能体开始执行，**不需要智能体结果回执**（不占异步邮箱）；但**需要"触发确认"信号**——目标节点确认"收到任务 + 执行器成功唤起"后返回"触发成功"；失败情形（目标离线 / `allow_ai_task` 关 / 执行器不可用或忙）返回"触发失败"及原因。**触发确认是节点层确认（任务送达并开始），非智能体结果回执。**
- **2.7.2** **异步邮箱与文本聊天通道隔离**：任务回执（按 correlation_id 配对、按 caller_id 归属）进**专门异步邮箱**，与 LocalSend 式文本聊天（人类会话视图）严格分开，不互相污染。
- **2.7.3** **执行器读回执**：无论是 CLI 还是 GUI 智能体，回复都由**执行器读取**后返回调用者节点，进入异步邮箱——确定性、可靠；**不采用"目标智能体主动用 skill 回调"模式**（把路由压给智能体推理、非确定、重复执行器职责，复杂度高）。
- **2.7.4** **回执到达通知**：异步任务回执返回后，**Web 面板有通知 + 非模态系统通知**（人类可见，方案 A+C）；下一次输入时提示调用者智能体 **check_mail**（懒拉取，不主动打断 AI）。
- **2.7.5** **异步执行链路（同一执行器，同一处理路径）**：异步与同步**共用同一执行器、同一处理路径**，执行器侧不感知任务是同步还是异步（2.7.1 目标侧对称）；**排队语义按执行器类型**（2.13.2）——非交互 CLI 忙时拒绝不排队，交互式 TUI / GUI 忙时排队、先到先处理；"异步"本质是**调用侧不阻塞**——调用者发出后继续干别的，回执进调用者节点的异步邮箱，下次输入时 `check_mail` 懒取。异步任务与同步任务在目标执行器上无优先级差异。

**原子化拆解（Given/When/Then）：**
- **2.7.G1** Given 调用者发起异步任务且 B 执行完成，When B 的执行器读到回复并返回调用者节点，Then 回执进入调用者节点的**异步邮箱**（按 caller_id 归属），且 Web 面板出现通知。
- **2.7.G2** Given 调用者发起异步任务，When 调用者继续处理别的事，Then 调用者不阻塞；直到下次输入时被提示 check_mail 才取回执。
- **2.7.G3** Given 调用者发起触发型任务，When 任务触达目标智能体，Then 目标智能体开始执行；无需回执、不占异步邮箱、无面板通知。

### 2.8 文本消息（即时聊天）
- **2.8.1** **可向对方节点发送文本消息**（类似 LocalSend 的点到点文本）。
- **2.8.2** 文本消息**存于双方各自的本地数据库**：发送方记 outbound（我向 X 发了文本），接收方记 inbound（我收到 Y 的文本），以 `correlation_id` 配对。
- **2.8.3** **即时聊天展示**：点到点文本以类似微信等即时聊天软件的形态展示，**有按对端聚合的聊天记录 + 消息会话视图**（左右气泡、时间戳、发送者、消息历史）。
- **2.8.4** **聊天载体 = 本地 Web 面板内页签**（「消息」页签），复用 FastAPI + 静态页。
- **2.8.5** **仅对方在线才可发送**：对方本身也是服务器；离线则发送失败，提示「目标不在线」。**不设已送达/已读回执，不做离线缓存补发**（匹配 TCP 极简存储不转发原则）。
- **2.8.6** **聊天记录各自本地、允许不一致**：每端从自己日志重建会话视图；任一端删除本地记录不影响对方。
- **2.8.7** **AI 可见聊天**：聊天不仅给人看，也给 AI 看。AI **仅能看到本节点作为一方参与的聊天**（本机 outbound + inbound，看不到他人节点间私聊）。
- **2.8.8** **AI 交互方式 = MCP 工具**：暴露 `send_text` / `list_conversations` / `get_chat_history`；AI 发消息成功得回执、失败得「目标不在线」原因并可报告人类。

**原子化拆解（Given/When/Then）：**
- **2.8.G1** Given 节点 A 在线，When A 的人类/AI 给在线节点 B 发文本，Then B 收到并落 B 本地库、A 落 outbound、双方各自会话视图均显示该消息。
- **2.8.G2** Given 目标节点 B 离线，When A 发文本给 B，Then 发送失败，A 本地记录失败并提示「目标不在线」，AI 可读到此结果并报告人类。
- **2.8.G3** Given 节点 A，When 其人类或 AI 查询聊天，Then 仅返回 A 作为一方参与的会话与消息历史（本地库聚合，不含他人节点间私聊）。

### 2.9 可见性与面板
- **2.9.1** **必须有 Web 面板**：状态变化必须让人类用户看到，不能无头、不能偷偷改变状态。
- **2.9.2** **面板只用 Web 面板**（不引托盘）；复用现有 FastAPI + `server/static/index.html` 底座。
- **2.9.3** **面板展示栏位（采纳建议清单）**，共**七块**（与第四章 4.1 导航一致）：
    - 概览/状态：本节点 node_id、名称、在线状态、运行时长、本机 IP、发现端口、**实际面板 URL**（`data/panel.url`，AI 经 MCP 概览工具可读，2.11.2）、**三个开关状态（allow_shell / allow_file / allow_ai_task）**
    - 节点列表：**已知对等节点**（含曾连上过的离线节点——离线不消失，2.1.9；每节点**同时显示 node_id 与名称**，name 为主显示、node_id 为寻址标识次显示；含主机、IP、在线/离线[含上次在线时间]、能力/插件、team）
    - 消息(聊天)：会话列表 + 即时聊天视图
    - 文件浏览器：远程文件浏览/下载/上传（独立页签，交互工具，见 2.4.6）
    - 执行器：**本机与远程统一列出**（本机完整显示：插件名、可用性自检结果 2.2.12、进程存活、忙碌/空闲/挂起（含原因与到期，4.3）、当前任务短码、任务队列长度、前提条件摘要 2.2.13；远程只显示能力列表，不深度查远程执行器状态）。**显示粒度：每执行器一个条目（含聚合状态与在途数），并发进程不单独显示多个条目**（2.2.9；队列长度仅排队型 TUI/GUI 有意义，非交互 CLI 恒 0，2.13.2）
    - 日志：**通信日志**（本节点本地 SQLite 日志 outbound/inbound，可按对端/correlation 过滤；**文件操作记录 push/pull/list_dir 并入**）+ **崩溃日志 node.log**（2.9.7）
    - 设置：team / 名称 / 开关 / 权限（run_as_admin）/ 清理等本机配置
- **2.9.4** **面板开关 = 三个"节点主动行为"开关**（均**仅本机可改**，状态随 beacon 广播）：
    - `allow_shell`：远程执行命令（shell_exec）
    - `allow_file`：远程文件读写 / 插件分发
    - `allow_ai_task`：远程任务消息**触发执行器唤醒** AI
    - **聊天（静态、无触发、给节点的）不需要开关，默认可用**。任一开关关闭 → 节点拒绝对应远程请求并在本机通信日志记录。
    - **开关关闭 ≠ 关端口**：端口照常监听（服务面板/文件/发现），**不因开关关闭而关闭**。
    - **关闭后仍可被发现**：beacon 照常广播，其他节点仍见其在线；beacon 载荷携带三个开关状态，对端可提前知晓哪些能力被关。
    - **本机 AI 不受影响**：开关只管远程请求，本机 AI 全权（经本地 MCP 查看/操作，不经远程请求路径）。
- **2.9.5** **开关只在本地本机改**：改动即生效并广播给对等节点；不提供远程改他人开关。
- **2.9.6** **面板不提供"关闭节点进程"**：不引外部守护/自愈层，**节点崩溃后由人类手动重启**；面板的"关闭"语义 = **仅熔断**（关闭受控能力），节点进程常驻不断、面板不自己砍自己。
- **2.9.7** **崩溃日志人类可读且 AI 可读**：统一结构化日志（时间戳/级别/事件），落 `data/node.log`；Web 面板展示；并通过 MCP 工具（如 `get_node_log`）供 AI 读取，便于人类/AI 排查崩溃原因。
- **2.9.8** **状态同步 = 单点真相 + 局部轮询刷新（方案 A）**：所有状态变化（人类面板操作 / AI 经 MCP 操作 / beacon 收到对端新状态）均落到**同一份本地状态**（单点真相），并触发 beacon 广播给对端；前端**复用 3s 局部数据轮询**检测本地状态变化并更新面板 UI，**不引入 SSE**。面板无需区分"谁改的"——只轮询本地状态，变了就更新，简单一致无竞态。
- **2.9.9** **面板交互细节（次要交互，实现阶段细化，不占核心闭环）**：
    - **文本参数（team / 节点名称等）**：输入后**点"保存"才生效**；保存后更新本地状态 + 广播 beacon（改名/换队立即让对端知道）。**输入框内容被修改但未保存时显示"未保存"标记**（如输入框变色/角标），避免改了忘保存。
    - **按钮开关（三开关）**：**切换即生效**，切换时有**明显状态变化**（开关翻转/颜色变化）+ **消息提示**（如"已关闭 allow_shell"），且提示**说明生效范围与影响**（如"远程将无法执行命令"），契合"不能偷偷改变状态"。
    - **保存失败反馈**：点保存后若失败（如 team_id 非法、重发现失败），**明确提示失败原因**，不静默。
    - **危险操作二次确认**：切换 team（断开旧连接、影响面大）**加一次确认弹窗**；开关类即时生效不另确认。
- **2.9.10** **执行器状态由节点核心持有**：执行器状态（可用性/存活/忙碌/空闲/挂起[含原因与到期，4.3]/当前任务/队列）由**节点核心**记录（它管任务调度），面板从节点核心读取（单点真相，与 2.9.8 一致）；常驻 daemon 执行器自持有状态，按需唤起执行器任务结束即退出，由节点核心记录其调度状态。**远程节点需查询本机执行器深态时，向本机节点发送 `executor_status` 申请**（受 `allow_ai_task` 管辖，2.16.4），节点是执行器的唯一对外窗口。

**原子化拆解（Given/When/Then）：**
- **2.9.G1** Given 本节点把受控开关关闭，When 来自其他节点的命令/文件读写请求到达，Then 被拒绝并在本机通信日志记录。
- **2.9.G2** Given 本节点修改受控开关，When 该节点广播下一次 beacon 时，Then 对端节点收到最新的受控状态。
- **2.9.G3** Given 节点进程崩溃，When 人类检测到其离线/失败，Then 人类手动重启节点进程；面板不提供杀进程入口，节点日志（人类/AI 可读）保留崩溃现场。
- **2.9.G4** Given AI 经 MCP 修改本机节点开关状态，When 状态变化落到本地状态并广播，Then 面板在下一轮 3s 局部轮询中检测到变化并更新 UI 为新状态。

### 2.10 安全模型与通信边界
- **2.10.1** **全放开通信推论（已确认）**：任何能访问局域网的主机/程序，只要知道协议格式，都能直接向任意节点发送协议消息以操作其能力（受该节点 `allow_*` 开关管辖），**无需经过"节点间正规通道"**。真正的防线是**每台节点的 `allow_*` 开关**，而非"消息从哪条路径来"。这是"纯明言 + 全放开 + 不认证"的必然结果。
- **2.10.2** **AI 直连远程节点 = 与正规通道等价**：AI 直接 curl / TCP 向远程节点发协议消息（可伪造 `sender_id`），在权限结果上与"经本机节点转发"等价，被全放开模型接受；远程节点按 `allow_*` + 受控检查决定执行与否，**不区分发送路径**。
- **2.10.3** **三种接入方式共存无冲突**：MCP server / 直接 run command / cli.py 均为"本机 AI 使用本机节点能力"的途径；本机 AI 全权（2.5.7），故无论走哪条结果一致；MCP 工具层过滤无意义（AI 可 run command 绕过，见 2.5.6）。
- **2.10.4** **节点 = AI 的宿主执行代理（沙箱绕过的设计）**：
    - **执行上下文在节点核心，不在 AI 侧**：AI 经 MCP 工具调用（`shell_exec` / 文件 / 任务 / 插件分发等）的**实际执行发生在节点核心进程**（宿主权限，可能管理员，2.14.6），而非 AI 自己的进程/沙箱。**MCP server 是薄转发桥**（由 AI 以 stdio 拉起，2.6.3）：仅参数校验、语义组装、结果回传，经本地连接（IPC/回环）把语义调用交给节点核心执行，**不自行执行有副作用操作**。
    - **沙箱 AI 经节点获得宿主能力（功能增强）**：保守/沙箱 AI（命令能力受限）只要能让 MCP server 连接到宿主节点核心，即经节点在宿主执行命令/文件/任务（权限 = 节点进程权限）——**绕开沙箱执行限制**获得完整功能。这是"AI 可控"的核心：**节点是 AI 通往宿主的可信执行代理**。
    - **安全暴露与缓解（对齐既定决策）**：
        - **本机 AI 全权（既定）**：2.5.7/2.9.4，开关只管远程请求、本机 AI 不受限——沙箱 AI 经本机节点同样全权。
        - **管理员权限由人类显式授予**：`run_as_admin`（2.14.6）需重启生效、AI 不能自行提权；**节点进程权限即 AI 经节点获得的能力上限**。
        - **全量可审计**：AI 经节点在宿主的一切操作都进 comm 日志（2.3.1）+ node.log（2.9.7），人类可见——绕过沙箱的操作**不隐蔽、可追溯**。
        - **远程仍受开关**：跨节点操作仍受目标节点 `allow_*` 管辖（2.9.4）。

### 2.11 部署、安装与启动
- **2.11.1** **发布方式 = 路线 A**：GitHub 源码 + 安装脚本；**一行命令下载安装引导**：
    - **Windows**：PowerShell `irm <url>/install.ps1 | iex`——自动**检测并引导 Python 运行时**（缺失时经 `winget` 安装 Python ≥3.10，不假设干净机器已装）+ 下载源码 + 装依赖 + 建桌面快捷方式（2.11.2）。
    - **Linux**：`curl -fsSL <url>/install.sh | bash`——**检测并引导 Python 运行时**（缺失时经系统包管理器安装）+ 下载源码 + 装依赖 + **可选安装 systemd 服务**（开机自启/无桌面后台运行）；有桌面时可选建 `.desktop` 启动器。
    - 代码核心为 Python，依赖外部二进制——**终端复用器**：Windows 用 **psmux**、Linux 用 **tmux**（执行器弹窗用，2.2.4）；**Syncthing** 同步引擎（2.4.7，按平台附带对应二进制）；**不需要 broker/mosquitto**，纯对等架构 + **a2a-sdk**（agent 协作协议 v1.0，2.16.3）。
- **2.11.2** **桌面快捷方式（启动或打开面板）**：安装脚本自动创建 Windows 桌面快捷方式（.lnk），指向启动器（`.bat` / `pythonw`），语义 = **启动或打开面板**：节点未运行 → 启动（无黑窗口，后台常驻 + 自动打开面板）；节点已运行 → **直接打开浏览器到实际面板 URL**（读 `data/panel.url`，2.11.3），不弹"已运行"错误。与"隐藏服务窗口"偏好一致。
- **2.11.3** **单实例保护**：节点启动时获取互斥锁/锁文件（如 `data/node.lock`）；**进程层**已运行再启动 → **拒绝并报错**：控制台/日志 `节点已在运行 pid=xxx`，经标准接口回执 AI 明确的"已运行"错误。**人类双击快捷方式不触发此错误**——启动器先查锁：未运行 → 启动节点；已运行 → 直接打开面板（2.11.2）。仅当人类直接运行启动脚本（而非走快捷方式）时才可能看到"已运行"提示。
- **2.11.4** **节点核心更新 = 仅人工部署**：节点核心代码**不设远程更新通道**（执行器插件可远程分发 2.2.10，节点核心仅人工替换 + 重启）；AI 不得修改节点程序文件（2.5.6）。若未来支持"官方仓库拉取更新"，须明确放宽范围并限定官方通道。

### 2.12 告警通道（面板之外）
- **2.12.1** **告警通道分层（避免模态轰炸）**：**MessageBox 模态弹窗只留给需人工确认的事件**（崩溃、重大错误）——Windows `MessageBoxW`（Linux `notify-send`，2.15.3）；**登录请求用非模态系统通知 + 窗口置顶**（2.2.14，不阻塞、靠置顶吸引注意，与 US-22 一致）；**异步回执到达用非模态系统通知**（notify-send/类似 Toast，不阻塞），仅提醒"有回执"供人类提示 AI 取信（2.7.4 面板通知保留）；**不引入托盘**。（回执到达若用模态 MessageBox 会频繁弹窗阻塞，属过度设计，故分层。）
- **2.12.2** **崩溃告警兜底**：节点崩溃时进程已退出、无法弹窗——改为**下次启动时检测上次异常退出**（如 `node.lock` 残留/上次退出非正常标记），启动时弹 MessageBox 告知用户"上次节点异常退出"，并提示用户**去读日志（data/node.log）或让本机 AI 读取日志**排查。

### 2.13 任务执行链路
- **2.13.1** **附件 P2P 直传（方案 A）**：调用方发起任务时，附件文件经点对点 TCP 直传到目标节点，落入**该任务的工作目录**（`data/executor_work/<agent_id>/<task_id>/`，2.2.11）；消息里带**本地路径**，执行器直接使用——替代旧的"上传中心 HTTP + URL + 下载"Claim-Check 链路。
    - **时序**：`task_id` 由**调用方节点核心在 submit 时先生成**——含附件时附件直传先行、任务报文后发（目标目录以该 task_id 命名）；目标节点拒绝任务（离线/开关关/执行器不可用）时**清理对应工作目录**。
    - **开关管辖**：附件直传**随任务走 `allow_ai_task`**（附件是任务的一部分，非独立文件操作），不适用 `allow_file`——`allow_file=off` 且 `allow_ai_task=on` 时带附件任务仍可执行。
- **2.13.2** **任务并发 + 忙碌语义（按执行器类型与并发度）**：每个执行器有**并发度**上限（2.2.9/2.2.15）：GUI 固定 1；非交互 CLI 默认 3 可配；交互式 TUI 默认 1（**v1 仅单会话排队，并发 >1 为后续版本**，2.2.9/2.2.16）。**在途任务数 ≥ 并发度 → 忙**。**非交互 CLI 忙时拒绝、不排队**（调用者在等回复，排队无意义，返回"忙碌"信号）；**交互式 TUI / GUI 忙时排队**（会话可复用 + 任务通常长，处理完再接下一个；后续版本并发 >1 时任务分发给空闲会话、会话内串行）。`executor_status`（2.16.4）据此返回"忙碌/空闲/在途/并发度/队列长度"供调用方决策。
- **2.13.3** **断线自动重连**：全连接 mesh 下，TCP 断线（节点重启/网络抖动）后**自动重连**对端节点；重连成功后恢复连接与消息通道。
- **2.13.4** **消息去重**：fire-and-forget 重发可能重复——按 **`msg_id` 去重**（2.16.6，传输层消息唯一 id，防重发重复），重复消息丢弃或幂等处理；`correlation_id` 仅用于任务关联（A2A Task），不用于去重。
- **2.13.5** **任务失败与重试策略（方案 A：不自动重试）**：
    - **节点不自动重试**：失败后由**调用者**（AI/人类）决定是否重发；节点只负责执行并回报失败原因。
    - **失败都进通信日志**：每次失败（投递失败/执行失败/超时）均记入双方本地通信日志（2.3.1），供审计排查。
    - **结构化错误码**：失败原因用结构化错误码回执，便于 AI 判断与决策——`offline`（目标离线）/ `disabled`（allow_ai_task 关）/ `not_installed`（执行器不可用）/ `busy`（非交互执行器忙）/ `suspended`（执行器被挂起，含原因标签如超额，4.3）/ `timeout`（超时）/ `agent_error`（智能体报错/崩溃）。
    - **重试幂等（两层）**：传输层重发靠 `msg_id` 去重（2.13.4）；**应用层重试靠调用者复用同一 `task_id`**（`submit_task` 幂等键，2.5.9 ⑤）——目标节点按 task_id 幂等，已执行/在途任务直接返回现状，不重复执行。

- **2.14.2** **去中心化、无 hub/broker**：不需要 MQTT 桥接、中心 API 或任何 broker 组件（2.1.1/2.1.8/2.11.1）；纯对等架构，不做可选 hub 模式。
- **2.14.3** **节点配置文件 `data/node_config.json`**：
    ```json
    {
      "node_id": "node-<hostname>-<随机短码>",
      "name": "我的节点",
      "team_id": "",
      "run_as_admin": false,
      "switches": { "allow_shell": true, "allow_file": true, "allow_ai_task": true },
      "peer_tcp_port": 0,
      "manual_peers": []
    }
    ```
    - **`node_id` 来源（自动生成，稳定身份）**：首次启动自动生成，格式 `node-<hostname>-<随机短码>`（如 `node-my-pc-a1b2c3`，hostname 取本机主机名、随机短码为生成值）；`node_id` 是**消息寻址依据**（寻址用，一般不手动改，改了寻址身份跟着变）；`hostname` 已内含于 node_id，**不需额外 hostname 字段**。`name` 才是用户可改的显示名（2.1.3），随 beacon 广播、改动不影响寻址。
    - **`node_id` 与 `name` 同时展示/可感知**：面板节点列表与 AI 接口**同时返回并展示 node_id 与 name**——`name` 为主显示（友好、可改、可重复），`node_id` 为次显示（唯一、稳定、寻址用）；**寻址一律用 `node_id`**（AI 不得只用 name 寻址，避免重名歧义）。
    - **新增字段**：`peer_tcp_port`（对等 TCP 端口，`0`=动态分配 2.1.5；预期被手动加入的节点应设固定值，2.1.10）、`manual_peers`（手动指定加入的对端地址列表，默认空，2.1.10）。
- **2.14.4** **环境变量配置项**（环境变量 + 配置文件加载；无 MQTT，P2P 直连）：`AGENT_NODE_CALLER_ID`（**CLI 智能体**的 caller_id；MCP 自动派生无需配置，2.6.4）、`AGENT_NODE_CONFIG_DIR`（配置目录）、`AGENT_NODE_INBOX_DIR`（统一收件目录）、`AGENT_NODE_DISCOVERY_PORTS`（发现端口集，2.1.5）。
- **2.14.5** **ASCII 命名规范**：所有目录/文件名**使用 ASCII 标准字符**（避免中文路径在 Windows 命令行 shell 执行时的转译问题）；如 `data/inbox/`、`data/sync/`、`executor_work/`。
- **2.14.6** **节点权限 = 可选项**：默认**普通权限**运行；**可"以管理员运行"**（启动时 UAC 提权，用于触达管理员权限的 GUI 智能体）；提供配置项 `run_as_admin: true/false` 个性化选择。**提示**：以管理员运行时，节点执行命令/文件操作也是管理员权限（风险更高），且执行器弹窗以管理员态出现；管理员态下向普通权限进程/窗口注入输入可能受 Windows UIPI 约束（提权后驱动普通权限 GUI 反而可能更难，2.2.5 可见深度 A 的窗口可见不受影响）。
- **2.14.7** **配置/状态持久化原则（重启不丢失）**：所有本机配置与状态修改**一律落盘、节点重启后保留**，无"内存态"配置：
    - **节点配置**（name / team_id / 三开关 / run_as_admin）→ `node_config.json`（2.14.3），修改即写盘（2.1.3/2.9.5）。
    - **执行器条目配置**（改名 name、并发度、会话策略）与**挂起状态（含原因与到期时间点，4.3）** → `executor_config.json`（2.14.1），修改即写盘，重启后挂起继续生效。
    - **known peers / inbox / 聊天记录** → `comm.db`（2.1.9/2.6.8）。
    - **插件** → `data/plugins/`（2.2.10）。

### 2.15 跨平台策略（Windows 优先，Linux 支持，Mac 预留）
- **2.15.1** **核心层跨平台**：通信/发现/存储/面板/协议/CLI 执行器一套代码，跨 Windows/Linux（纯 Python + socket + SQLite + FastAPI）。
- **2.15.2** **Windows 专属**：MessageBox 弹窗（2.12）、GUI 适配器（workbuddy/traework，UIA/deeplink/CDP）、桌面快捷方式（.lnk）、无黑窗口（pythonw）。
- **2.15.3** **Linux 支持**：启动无黑窗口（nohup/systemd 后台，2.11.1 可装 systemd 服务）；桌面通知用 `notify-send`（替代 MessageBox，2.12.1）；**无 DISPLAY（无桌面/SSH）时 `notify-send` 不可用 → 系统通知降级为「Web 面板通知 + 日志」**（面板 127.0.0.1，2.1.5）；**不做** GUI 适配器、桌面快捷方式、计划任务集成（用户自用 cron）。**CLI 执行器弹窗边界**：有 DISPLAY（图形会话）→ `attach_visible` 弹图形终端（xfce4-terminal 等）；无 DISPLAY（服务器/SSH）→ `attach_visible` 自动降级 headless 不弹，CLI 照跑 + 结果文件契约取回（2.2.6）。**面板访问（无桌面服务器）**：面板绑定 127.0.0.1（2.1.5），人类经 **SSH 端口转发**访问（如 `ssh -L <本地端口>:127.0.0.1:<面板端口> user@服务器` 后浏览器打开 `<本地端口>`）。
- **2.15.4** **GUI 执行器按平台可用性启用**：Linux 无 GUI 智能体品牌即不加载对应适配器（2.2.12 能力自检覆盖）。
- **2.15.5** **Mac 暂不排期**：架构预留（平台适配层留接口，未来加 Mac 分支）。

### 2.16 协议（复用 A2A 协作层 + 自研节点控制面）
- **2.16.1** **分层总述**：协议分两层——**agent 间协作层采用 A2A 标准**（Linux Foundation，v1.0 于 2026-03-12 定稿，**传输无关**：官方参考实现走 HTTP(S)+SSE，规范支持 **Custom Protocol Bindings**——在 Agent Card `supportedInterfaces` 声明自定义传输，先例含 WebSocket、EMQX A2A-over-MQTT），**节点控制/发现/聊天层自研**（纯对等、明文、极简）。**我们采用「A2A 数据模型/任务语义 + 自研 P2P TCP 传输」**——复用其 Task/Message/Part/Artifact 数据结构与任务状态机语义；**不声称实现合规的 A2A custom binding**（A2A 规范要求 custom binding 暴露全部核心操作——streaming、push notification、cancel 等，本设计明确不做：无 stream 接口 2.2.15、不做任务取消 2.16.3、回执走轮询 2.6），`supportedInterfaces` 字段结构仅作 mesh 内部描述沿用；不互操作广义 HTTP 生态其他 A2A 智能体（无需，执行器本就自研包装）。
- **2.16.2** **发现/状态类（走 UDP beacon，自研，不走 TCP）**：
    - `beacon`：`{ node_id, name, team_id, ips, ports:{peer_tcp, discovery[]}, switches:{...}, capabilities:[...], sync_device_id, seq }`——`node_id` 为自动生成的稳定身份（格式 `node-<hostname>-<随机短码>`，2.14.3，hostname 已内含、不设独立字段）；`seq` 去重（2.1.5）、**switches 携带三开关状态**（对端提前知晓能力开关）、**name/team_id/switches 即本机配置的传播通道**。**beacon 不携带 `run_as_admin`**（权限是本机内部的事，不广播给对端）。**`capabilities` 结构（每执行器条目一条，由 2.2.12 能力自检产生）**：`{ agent_id, name, executor_type, concurrency }`——只广播**当前可用**条目（探测不到不广播，2.2.12）；`name` 随改名（`rename_executor`）在下一次 beacon 更新传播给对端展示；此即远程 `list_executors` 被动可见的"能力列表"来源（2.9.3，深态按需查，2.16.4）。
    - **`sync_device_id`**：本机 Syncthing 设备证书指纹（device ID）——2.4.7 设备配对引导的数据来源；同步关闭的节点该字段为空、不参与互配。
    - **beacon 始终广播可见**：无论 team 是否一致，所有节点都能收到并读到载荷；team 隔离（2.1.7）只作用于"是否建立 TCP 连接/互通"，不阻止 beacon 信息的读取——因此退队/新 team/开关变化经 beacon 天然可见，无需额外通知消息。
- **2.16.3** **agent 协作层 = A2A 标准（2.7 任务/2.6 异步）**：
    - **部署边界**：A2A 是"调用方与被调方"的应用层契约，**Client 与 Server（执行器）都在各自节点进程内**——节点作为 A2A Client 发起任务，本地执行器作为 A2A Server 被调用；**跨节点传输走自研 P2P TCP 明文通道**（A2A 消息作为 custom binding 负载封装，2.16.1），目标节点收到后路由给本地对应执行器。**版本锁定 A2A v1.0**，消息/数据模型与规范一致（JSON-RPC 2.0 方法、camelCase 字段、ISO 8601 UTC 时间戳）。
    - **A2A 核心概念映射**：Agent Card（能力发现，≈ 2.2 能力广播）→ 节点为每个执行器维护 Agent Card 结构（字段沿用 A2A v1.0，`supportedInterfaces` 声明自研 TCP binding），其摘要（agent_id/name/executor_type/concurrency）经 beacon capabilities 广播（2.16.2）——**仅作 mesh 内部描述，不对外发布 .well-known、不声称 A2A 合规**（2.16.1）；Task 生命周期（submitted/working/input-required/completed/failed/canceled）→ 覆盖 2.7 的同步/异步/触发型与状态回执（**cancel 不用**——任务取消不做：统一接口 2.2.15 无 cancel 方法，执行器不实现取消；放弃/重发由调用者决定，2.13.5）；Message/Part → 消息格式；Artifacts → 任务结果（配合 2.2.11 结果文件契约）。
    - **接入 A2A SDK**（`pip install a2a-sdk`，v1.0，Apache-2.0）；执行器作为 A2A Server 被调用，节点作为 A2A Client 发起任务——**不依赖 CLI/GUI 智能体本身实现 A2A**（执行器包装层自行实现协议端点，见 2.2）。复用 SDK 的数据类型（Task/Message/Part/AgentCard）+ 消息层，传输走自研 TCP binding（2.16.1）。
    - **附件**：任务附件经自研 P2P 直传（2.13.1）落到执行器工作目录，A2A Message 中带**本地路径**（替代 URL）。
- **2.16.4** **节点控制/文件/聊天层（走 TCP，自研；线级帧格式与统一信封见附录 A）**：
    - **开关管辖范围**：**控制/文件类**报文接收方按三开关（2.9.4）检查（shell/file 关则拒）；**聊天（`text_request`）不受开关管辖**（静态、无触发、给节点的，默认可用，见 2.9.4）。
    - `text_request`：聊天文本（2.8），`{ target_node_id, payload:{ text, session_id? } }`——不受开关管辖
    - `shell_exec` / `shell_result`：命令执行——受 `allow_shell` 管辖
    - `file_push` / `file_pull` / `file_list`：文件操作（2.4；回执 `file_ack` / `file_result` / `file_list_result` 与分帧规则见附录 A.4）——受 `allow_file` 管辖
    - `plugin_sync` / `plugin_sync_result`：**插件分发后的重扫/重载触发**（2.2.10）——`{ target_node_id, payload:{ changed_plugins?: [agent_id] } }`，目标节点重扫 `data/plugins/` 注册表：新增插件纳入能力广播；更新且为交互式执行器 → **重启该插件进程**才生效；返回 `plugin_sync_result`（成功/失败 + 受影响插件 + 已重启执行器）给发起方并记双方日志——**受 `allow_file` 管辖**（插件分发属文件类能力，2.2.10）
    - `executor_status` / `executor_status_result`：远程查询本机执行器深态（可用性/忙碌/在途/并发度/队列/当前任务/挂起[含原因与到期，4.3]/交互式会话数），**受 `allow_ai_task` 管辖**（执行器状态查询属"AI 任务"范畴，是调用执行器的前置动作，也是远程 `get_executor_status` / `list_agent_sessions` 的底层通道，2.5.9 ⑤；`allow_ai_task` 关闭时拒绝查询，一致）
    - `ping` / `pong`：TCP 探活（2.1.6 在线检测）——不受开关管辖（在线检测必需）
- **2.16.5** **本机配置（team/name/三开关）不走网络报文**：修改操作仅本机 MCP/面板执行；**变更结果经 beacon 载荷传播**给远程节点感知（远程靠收 beacon 更新，无需远程主动查询/推送）。
- **2.16.6** **去重与关联（自研传输层）**：传输层报文带 **`msg_id`（消息唯一 id，去重 2.13.4）** 与 **`correlation_id`（A2A Task 关联）**，二者区分；A2A Task 自身有唯一 ID，`msg_id` 用于传输层防重发重复。统一信封字段（`v` / `msg_id` / `type` / `sender_node_id` / `target_node_id` / `correlation_id` / `payload`）定义见附录 A.3。

### 2.17 健壮性与可靠性
- **2.17.1** **故障与边界检测 → 确定的阻断/降级提示**：断网（TCP 断线重连 + `offline` 错误码）、超时（`timeout` + 已观察部分）、依赖不可用（`not_installed`，2.2.12 自检阻断）、并发竞争（串行队列 2.13.2 + caller 隔离 2.6.5）——均定义**确定的错误码/提示**，**多走阻断提示而非降级**（与"极简/不缓存/不自动重试"决策一致：聊天不做离线缓存 2.8.5、节点不自动重试 2.13.5）。
- **2.17.2** **状态变更操作幂等**：开关切换 / team 切换 / 改名等**状态变更必须幂等**（重复执行结果一致，如"关闭"再"关闭"仍是关闭）；文件/任务类操作靠 `msg_id` 去重（2.13.4）。
- **2.17.3** **冲突检测**：文件同步同名冲突（2.4.7，最后写入覆盖）、push 目标路径冲突等有确定策略；多客户端并发访问经 caller 隔离（2.6.5）不互相干扰。
- **2.17.4** **严禁吞噬异常**：任何异常必须记录**结构化日志**（2.9.7 node.log + 2.3.1 通信日志），不得静默吞掉；失败都进日志（2.13.5）。
- **2.17.5** **事务原子性**：SQLite 写入用事务（comm.db 并发写安全，2.6.8）；文件传输"要么完整要么不落盘"（半写清理）。
- **2.17.6** **文件传输完整性校验**：push / sync / pull 文件到达目标后**校验完整性**（发送方先算 **SHA-256 哈希**，接收方校验大小 + SHA-256）→ 确认"文件完整到达预期文件夹"后才回执成功；不完整 → 失败回执 + 清理半写文件（呼应 2.13.5 失败进日志）。
- **2.17.7** **AI 自主排查与修复（故障分级 + 诊断入口 + 日志感知 + 深文档门控）**：
    - **故障分级与 AI 响应阶梯**：
        - **级别 0 正常**：AI 走 MCP 工具（2.5.9）。
        - **级别 1 MCP 异常、节点核心仍活**：AI 降级用 `cli.py`（2.5.1 双入口）+ `cli.py diag` 诊断，读日志与 comm.db；经标准接口修复（`restart_plugin` / `plugin_sync` 2.16.4 / 调开关）。
        - **级别 2 节点核心异常但端口可探测**：AI 依深文档线格式用原始报文探测（`ping`/`pong`、`shell_result` 等）定位故障面；接口修不了 → 给出诊断结论 + 建议人类重启（2.9.6）。
        - **级别 3 节点进程死亡/无响应**：AI 无法连接，读日志定位原因，给人类重启指引（2.9.6/2.11.3）。
    - **诊断入口 `cli.py diag`（自检命令）**：一键结构化健康检查——本地配置可读、发现端口监听、业务 TCP 端口、MCP server 存活、插件加载（`check_capability` 汇总）、comm.db 可写、beacon 收发、已知节点可达性；输出结构化结果供 AI 判读。
    - **接口可探测性原则**：**不为每个接口加测试钩子**；接口本身须**可探测**——确定性请求/响应、结构化结果与 2.13.5 错误码、`ping/pong` 探活、日志落盘（2.17.4）；AI 依线格式即可**无副作用**探测；有副作用的操作（shell/文件/任务）用于修复而非探测。
    - **故障排查时日志全量可感知**：排查/维修时，AI 可感知**所有节点相关程序的运行日志**——node.log（2.9.7）、comm.db 通信日志（2.3.1）、执行器插件运行日志、MCP server 日志、子进程日志（如 Syncthing）等；经 `get_node_log`（支持指定来源，2.5.9 ⑥）或直接读取 `data/` 下日志文件获取（AI 本就可读本机文件，2.5.4）。
    - **深文档（架构 + 协议接口标准）门控**：提供**完整架构 + 全部协议报文/接口标准**的深文档（如 `docs/协议与架构.md`）——**默认不向 AI 暴露、不随 SKILL 分发**（2.5.4）；AI 不得随意调用/访问；**仅重大意外 + 人类明确允许**时提供给 AI 详细排查（替代解读源码猜接口）。**文档级约束，不技术设防**（本机 AI 本可读源码，2.5.4/2.5.6）。
    - **修复边界**：AI 的"修复"止于**标准接口层**（重启插件/重扫/开关/配置，经 cli.py 或修复后恢复的 MCP）；**不得改源码/打补丁/改配置文件**（2.5.6）；节点进程死亡由人类执行重启（2.9.6）。

### 2.18 环境前提（代理/防火墙配置）

- **2.18.1** **mihomo（Clash Meta）代理是真实障碍，须配置局域网直连**：TUN 模式接管系统全部流量，若局域网直连 IP 被判走代理规则，节点间 TCP 会被转发到代理服务器导致互连失败（fake-ip 不影响——beacon/互连用 IP 直连非域名，但 TUN 规则分流是致命风险）。
- **2.18.2** **mihomo 必须的配置（部署前提）**：在 mihomo 配置中加入以下规则，保证局域网直连 + 多播/UDP 放行：
    ```yaml
    rules:
      # 局域网段直连（不走代理，否则节点互连失败）
      - IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
      - IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
      - IP-CIDR,172.16.0.0/12,DIRECT,no-resolve
      # 多播/广播（beacon UDP 发现）直连
      - IP-CIDR,224.0.0.0/4,DIRECT,no-resolve
    dns:
      # 局域网域名/主机名走真实 DNS 而非 fake-ip
      fake-ip-filter:
        - "+.local"
        - "+.lan"
    ```
    **要点**：对等通信 TCP 端口动态（2.1.5）无法按端口白名单，只能按 IP 段 DIRECT；**面板仅本机回环访问（127.0.0.1，2.1.5）不走代理**；UDP 广播（beacon）必须放行。
- **2.18.3** **TUN 未配 = 大概率互连失败（排查依据）**：若开启 TUN 模式但未配置 2.18.2 的局域网 DIRECT 规则——**beacon UDP 广播大概率被丢弃（代理不支持广播，互相发现失败）**；即便已知对方 IP，局域网 TCP 也会走代理导致连接失败。**例外**：仅当用户 mihomo 模板本身已含局域网 DIRECT 规则才可通（不可依赖）。
- **2.18.4** **披露方式与 AI 排查**：mihomo 配置作为**部署前提条件**写入安装引导、面板提示与 **Skill（2.5.5）**（类似 2.2.13 执行器前提披露）；AI 可感知本机网卡/IP 异常（`ipconfig`/`ip addr`、路由表、beacon 收不到对端），检测到"局域网互连失败但本机网络正常"→ 提示可能 TUN 代理未配局域网直连 → 读 Skill 给出 2.18.2 配置指引。
- **2.18.5** **防火墙（部署前提，新增）**：
    - **Windows**：UDP 广播（发现端口集）+ 对等 TCP 入站首次运行会触发防火墙提示，**公用网络配置下被静默拦截直接失败**。对等 TCP 端口动态（2.1.5）无法按端口开规则——**按程序放行**：安装脚本（2.11.1，需管理员）为本节点程序添加入站规则，并提示用户将网络设为"专用网络"。
    - **面板无需规则**：绑定 127.0.0.1 仅本机回环（2.1.5），不涉防火墙。
    - **Linux**：不自动改防火墙；安装脚本检测 ufw/firewalld 并**给出放行提示**（发现端口集 UDP），由用户自行执行。

## 四、Web 面板（去中心化后的可观察性）

去掉 hub 后，面板**跟随节点**，每个节点自带一个本地 Web 面板，是人类与节点交互的主界面。**不过度设计，但实现完整功能且让人类稳定交互、可靠显示节点状态。**

### 4.1 整体结构（SPA，左侧导航 + 右侧内容区）

单页应用（SPA），左侧固定导航 + 右侧内容区，七视图：

| 导航项 | 视图 | 对应需求 |
|---|---|---|
| 概览 | 本机状态 + 三开关 + 本机执行器摘要 | 2.9.3 |
| 节点 | 已知节点列表（node_id+名称+在线/离线/能力/开关） | 2.9.3、2.1.6、2.1.9 |
| 消息 | 即时聊天（会话 + 气泡）+ 异步回执通知 | 2.8、2.7.4 |
| 文件 | 远程文件浏览器 | 2.4.6 |
| 执行器 | 统一执行器视图（本机+远程全部可调用） | 2.9.10 |
| 日志 | 通信日志 + 崩溃日志 | 2.3、2.9.7 |
| 设置 | team/名称/开关/权限/清理等本机配置 | 2.9.9、2.14.6、2.6.9 |

**状态灯常驻顶部**：本机运行状态（**运行中 / 忙碌**，忙碌=有任务处理中）实时可见，不随页面切换隐藏——可靠显示节点状态；无「异常」空壳态（故障走崩溃告警 2.12.2 + node.log 与对应视图，不入灯）。

### 4.2 各视图功能

**概览**：本机信息（node_id、名称、team_id、IP、运行时长）；三开关（按钮式，切换即时生效 + 状态变化 + 影响提示，2.9.9）；本机执行器状态摘要（可用/忙碌/挂起/当前任务）。

**节点**：**已知对等节点列表**（node_id + 名称 + team + 能力 + 在线/离线[含上次在线时间]；离线节点不消失，2.1.9；beacon 超时 + TCP 探测 2.1.6）；点节点看详情（能力、开关状态、地址、可发起任务/聊天）。

**消息**：左侧会话列表（按对端聚合）+ 右侧气泡聊天（左右气泡、时间戳、发送者，2.8.3）；输入框发送文本，对方离线提示"目标不在线"（2.8.5）；异步回执通知在此显示（2.7.4）。

**文件**：远程文件浏览器（路径栏 + 目录列表 + 进入/返回上级 + 下载单文件/整树 + 上传到当前目录，2.4.6）；本地收件目录（data/inbox/）与同步目录（data/sync/）快捷入口。

**执行器（统一视图）**：本机与远程执行器**同一页面列出**（都标归属节点列，因均可用）。每执行器：归属节点、**name（可改名，2.5.9 ⑦）**、executor_id（次显示）、在线、操作入口（调用/查看）。**本机执行器**显示完整状态（空闲/忙碌/挂起[含原因与到期]、在途/并发度、当前任务、队列、前提摘要，4.3）；**远程执行器**仅显示在线 + 能力列表（beacon 来源，2.9.3），深态按需经 `executor_status` 查询（2.16.4）。**显示粒度：每执行器一个条目，并发进程不单独显示**（2.2.9）。

**日志**：通信日志（本地 outbound/inbound：时间、方向、类型、结果，2.3.1）；崩溃日志 node.log 可读（2.9.7）。**执行器详细状态归「执行器」视图**（4.2 执行器）。

**设置**：文本参数（名称/team）输入 + **保存按钮**才生效 + 未保存标记（2.9.9）；三开关集中管理；权限可选项 run_as_admin（2.14.6）；危险操作（切 team）**二次确认**（2.9.9）；清理机制（清已读/超期未读，2.6.9）。

### 4.3 执行器归属与挂起（含超额原因）

- **归属关系**：执行器是节点的属性，**挂在归属节点下显示**；但本机与远程执行器**统一列在一个「执行器」页面**（均可用），归属通过"节点列"标注，入口一致。
- **挂起 = 唯一的手动干预状态（超额只是原因标签，非独立状态）**：智能体额度/状态问题**执行器无感知**，因此由**人类感知并管理**——人类在面板挂起某执行器，或指示 AI 经 MCP 挂起（2.5.7 能力对等映射）。挂起时可选填：
    - **原因标签**：`超额`（额度用尽）/ `手动` 等；标"超额"即挂起 + 原因=超额，调用时额外提示"该智能体可能已超额度"。
    - **到期时间点（可选）**：人类/AI 设定**具体到期日期或时间点**（如 `2026-08-20 12:00`，或"从现在起 2 小时"换算为时间点），**到点自动恢复**（额度刷新后可正常工作）；不设到期则长期挂起，人类可提前手动恢复。
    - 挂起与在线/离线**正交**（执行器无论是否在线都能被挂起）；挂起期间拒绝任务（返回 `suspended` 错误码，2.13.5）。
- **AI 接口（本机，2.5.7 能力对等映射）**：本机 AI 经 MCP 可**读取**执行器挂起状态/原因/到期时间（`get_executor_status`），并**操作**挂起与恢复（`set_executor_suspend`，可设原因与到期时间点），与人类面板操作等价；远程经 `executor_status` 协议只读查询（2.16.4，受 `allow_ai_task` 管辖），不可改他人挂起状态。
- **执行器详情操作**：点某执行器——本机：完整状态 + 前提条件摘要 + 操作（重启插件/挂起/恢复）；远程：能力摘要 + 前提条件 + "调用"入口（受 allow_ai_task 管辖，2.16.4）。

### 4.4 交互与可靠性

- **局部数据轮询（3s）**：状态/节点/日志等**只更新对应 DOM，不整页刷新**——解决"选中文字被刷掉"（2.1.6）。
- **状态同步单点真相**：所有状态变化（人类/AI/beacon）落同一份本地状态，面板轮询读之（2.9.8）。
- **操作反馈**：每次操作（发送/保存/切换/挂起/恢复）有明确成功/失败提示，不静默。
- **错误展示**：错误码（offline/disabled/not_installed/busy/suspended/timeout/agent_error，2.13.5）以可读文本 + 原因展示，失败进日志。
- **状态变化面板实时可见、可追溯**，杜绝「无头偷偷改状态」。

## 五、施工与验收策略

协议报文（2.16）与插件接口（2.2）**已定案**，作为 AI 施工的硬契约。施工策略如下：

- **1. 协议定稿时机（分层）**：**跨节点核心协议已定死**（2.16——beacon 发现、A2A 协作层、节点控制面报文、错误码，+ **附录 A 线级帧格式/统一信封**），因为这是"接缝处"：不同节点、不同时间施工，协议不一致即不兼容；**执行器插件接口已定稿**（2.2.15：`submit/is_done/get_result` + 生命周期 + 状态 + 注册表；结果取回统一走结果文件契约 2.2.11）、**实现细节留施工**（各品牌适配器内部实现，如何驱动窗口/会话/CLI 进程）；**节点内部模块接口**（核心↔面板↔MCP）可留施工（同进程内自洽即可）。
- **2. 测试与验收方案（三层）**：
    - **单元测试**：模块级（通信/存储/执行器/文件），每模块独立可测。
    - **集成测试**：节点间互操作（两节点互通、消息往返、A2A 任务生命周期、文件传输）。
    - **验收测试**：按**用户故事（第零章 US-1~30）逐条验证**，每个 US 有 Given/When/Then（第二章已有部分），测试据此编写——**验收标准 = 用户故事**。
- **3. AI 施工验收门禁**：**每个模块完成须过对应测试才合格**；失败只改该模块（模块化 + 契约先行 + 依赖倒置，通信层/执行器/文件/面板靠接口隔离，单点错误被局部捕获，不会导致整体推倒重来）。
- **4. 测试桩/模拟器**：提供 **mock 执行器 / 假 CLI**，让 AI 施工时可不依赖真实智能体独立测试执行器（如用假 CLI 模拟输出验证 submit/is_done/get_result 逻辑，2.2.15）。
- **5. 模块化设计保证**：模块边界 + 依赖倒置，契约先行，各模块可并行/独立施工（靠 mock/stub 对测），保证智能体犯错不扩散到整体。

## 附录 A、自研 TCP 线级协议（施工硬契约）

2.16 各报文的**线级格式**在此定稿（与 2.2.15 插件接口同级的施工硬契约，随本方案提供给施工 AI；`docs/协议与架构.md` 为其完整展开版深文档，受门控 2.17.7）。beacon 为 UDP 明文 JSON（载荷见 2.16.2，无帧封装），不走本附录。

### A.1 连接模型
- 每对互通节点保持**一条长连接**（全连接 mesh，2.1.8）；断线自动重连（2.13.3）。
- **连接建立后双方各发首帧 `ping`**（信封含 `sender_node_id`，payload 含本节点 `team_id`）完成身份交换；**team 不一致 → 回 `error`（`disabled`，detail 注明 team mismatch）并关闭连接**——team 隔离在 TCP 连接层强制执行（2.1.7），beacon 只是预筛。
- **去双连接**：双方同时发起时各自检测到与同一对端存在两条连接 → 按 **node_id 字典序保留"较小节点发起"的那条**、关闭另一条（双方独立计算、结果一致）。

### A.2 帧格式（全部 TCP 数据统一二进制帧）
```
[1 字节 frame_type][4 字节大端长度 N][N 字节载荷]
```
- `0x01` = **JSON 控制帧**：载荷为 UTF-8 JSON（信封见 A.3）。
- `0x02` = **文件块帧**：载荷 = `16 字节 file_transfer_id` + `4 字节大端 seq` + 原始文件字节（默认块 1 MiB，无 base64 开销）。
- 单帧载荷上限 **8 MiB**：控制帧超限或长度非法 → 回 `error`（`bad_frame`）并关闭连接（防畸形帧耗尽内存）；文件数据按块分帧，天然低于上限。

### A.3 JSON 信封（控制帧统一结构）
```json
{
  "v": 1,
  "msg_id": "<uuid4>",
  "type": "text_request | shell_exec | shell_result | file_push | file_pull | file_list | file_list_result | file_ack | file_result | plugin_sync | plugin_sync_result | executor_status | executor_status_result | a2a_request | a2a_response | ping | pong | error",
  "sender_node_id": "node-xxx",
  "target_node_id": "node-yyy",
  "correlation_id": "<uuid4 或 null>",
  "payload": { }
}
```
- `msg_id`：传输层去重键（2.13.4）；`correlation_id`：请求/回执关联（A2A 任务即 task_id，2.16.6）；字段命名统一 `node_id` 体系（2.5.9 命名统一，旧称 `target_id` 废止）。
- 未知 `type` → 回 `error`（`unsupported_type`），**不关闭连接**（留向前兼容余地）。

### A.4 文件传输分帧（push/pull 复用 mesh 长连接，2.1.5）
- **push**：`file_push`（payload：target_path、size、sha256、file_transfer_id）→ 接收方回 `file_ack`（同意/拒绝 + 原因码）→ 发送方连发 `0x02` 块帧（同 file_transfer_id、seq 递增）→ 接收方校验大小 + SHA-256（2.17.6）后回 `file_result`（成功/失败）；失败清理半写文件（2.17.5）。
- **pull**：`file_pull`（payload：path）→ 对端回 `file_ack`（含 size/sha256/file_transfer_id）→ 对端按 push 同机制反向推块帧 → 请求方校验后回 `file_result`。
- **多路复用**：并发传输按 `file_transfer_id` 区分，块帧与控制帧在同一条连接上交错传输，互不阻塞。

### A.5 A2A 封装
- `a2a_request` / `a2a_response` 的 payload = **完整 JSON-RPC 2.0 对象**（camelCase 字段、ISO 8601 UTC 时间戳，2.16.3）；信封 `correlation_id` = A2A task_id。
- **附件不经 A2A Message 传输**：先按 A.4 直传到任务工作目录（2.13.1 时序：附件先行、任务报文后发），A2A Message 中只携带本地路径。

### A.6 错误响应
- 任何处理失败回 `error` 控制帧：payload = `{ "code": "...", "message": "...", "detail": ... }`。
- `code` 取 2.13.5 错误码（offline/disabled/not_installed/busy/suspended/timeout/agent_error）；**开关拒绝统一 `disabled`**（detail 注明哪个开关）；传输层补充 `unsupported_type` / `bad_frame`。

### A.7 连接保活
- `ping` / `pong` 控制帧：默认每 5s 一帧；连续 3 次无 `pong` → 判连接断开 → 触发重连（2.13.3）。与 beacon 在线检测（2.1.6）独立并行、互不替代。
